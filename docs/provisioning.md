# Authentication preparation and recovery

Use the YubiKey for Git signing, initial installation or recovery, decrypting the bootstrap identities for SOPS work, and reading which sites hold FIDO credentials on a card. On NixOS desktops, routine configuration applies use the root-only age identity inside LUKS. SSH prefers the host's own key, unlocked through KWallet, and automatically falls back to selected 1Password keys. Automatic account login is not configured. On non-NixOS hosts, routine applies use a user-owned age identity, and each host has its own SSH key; see [Recover once on a non-NixOS host](#recover-once-on-a-non-nixos-host) and [SSH key on a non-NixOS host](#ssh-key-on-a-non-nixos-host). A macOS host does the same, and its card PIN can be saved in the macOS Keychain; see [YubiKey PIN on macOS](#yubikey-pin-on-macos).

## Before erasing the existing OS

The repository's `keys/` directory stores two public keys and no private key. `signing.asc` is the current signing identity, fingerprint `621512777E6933FEB4458FDC4945855D4F283F05`. `signing-legacy.asc` is the retired rsa2048 key, kept so commits and tags signed before the rotation still verify. It is deliberately the copy from before that key was revoked: with the revocation merged in, `git verify-commit` fails on every pre-rotation commit, because git treats gpg's revocation warning as an error even though the signature itself is still good. Confirm that the actual card provides signing and encryption subkeys.

```sh
gpg --show-keys --with-fingerprint keys/signing.asc
gpg --card-status
```

Do not export private OpenPGP keys to disk. If no usable encryption subkey is available, fix the card's key configuration before erasing the disk.

Generate a dedicated age identity and record its public recipient. Handle temporary plaintext only in a private tmpfs directory. Do not enable shell tracing.

The preparation helper does this. It runs on the pre-migration host, from the development shell, because `age` is not otherwise installed there. It generates the identity in a private runtime directory, encrypts it to the card's subkey, verifies that the result decrypts back to the same identity, records the public recipient, and removes the plaintext. It refuses to run as root and refuses to overwrite an existing host directory.

```sh
nix develop
./scripts/prepare-age-identity \
  --host <host> \
  --recipient 621512777E6933FEB4458FDC4945855D4F283F05
```

Replace `<host>` with the machine's directory name under `hosts/`. It writes `secrets/bootstrap/<host>/age-key.asc` and `secrets/bootstrap/<host>/recipient.txt`.

`.sops.yaml` has no per-host anchors: each creation rule lists its age recipients inline, comma-separated. Append the recorded recipient to the `age:` list of every rule the host needs. Every host whose recipient appears in a file's rule can decrypt that file. Adding a recipient to an existing file's rule requires re-encrypting it, for example with `sops updatekeys -y secrets/tokens.yaml`; [adding a host](adding-a-host.md#add-the-recipient-to-sopsyaml-and-re-encrypt) gives the commands for every file. Create or update the token YAML in a private temporary directory using the schema in `secrets/README.md`. Prepare tokens and usernames for GitHub, GitLab.com, and git.jpi.app. Do not pass tokens as command arguments.

```sh
umask 077
secret_tmp=$(mktemp -d /run/user/"$(id -u)"/nix-secrets.XXXXXX)
# Encrypts for every recipient listed in the matching .sops.yaml rule:
sops --encrypt \
  --input-type yaml --output-type yaml \
  "$secret_tmp/tokens.yaml" > secrets/tokens.yaml
```

Validate the encrypted files without printing decrypted output. Confirm that the age public recipient obtained through GPG bootstrap recovery matches the recorded value. Do not `git add` plaintext. Commit only the two encrypted files, the public recipient, and `.sops.yaml`. Remove the temporary directory after verification.

To verify code without a real card or tokens, use only the fake credentials generated by the `auth-provisioning` VM check (`nix build --no-link .#vmChecks.auth-provisioning`) and the fixtures in `tests/test_publish_cli_auth.py`. Do not install these fixtures as real authentication data.

## Recover once on the installed NixOS

First, log in as h82 with the bootstrap configuration's public GPG key and user agent in place. Card checks and public-key registration must not become requirements for routine rebuilds. Run the recovery helper from the clone; it resolves the running host, decrypts through h82's GPG agent, and pipes the result to the root installer.

```sh
./scripts/recover-age-identity
```

Pass `--host <host>` when the hostname is not the configuration name, which is the case in the installation media and inside `nixos-enter`. See `secrets/README.md` for the pipeline it runs and the boundary it preserves.

The recovery helper verifies the expected age public recipient and atomically installs `/var/lib/sops-nix/key.txt` with ownership root:root and mode 0600. An invalid identity does not overwrite the existing key. Once the key is ready, run the following command to apply the configuration, including user authentication files.

```sh
sudo nixos-rebuild switch --flake .#<host>
```

Use the same command for later applies. It works with the YubiKey disconnected or Secret Service and 1Password locked. The gh/glab authentication files are user-owned regular files with mode 0600. The next apply restores their declared contents. Do not repeat manual `gh auth login` or `glab auth login` as follow-up steps.

## Recover once on a non-NixOS host

A non-NixOS host keeps its age identity in the user's home, not under `/var/lib/sops-nix`. Recover it once, after the bootstrap output is applied. [Adding a host](adding-a-host.md#first-setup-on-the-machine) gives the full first-setup order. A macOS host recovers its identity the same way; its first-setup order is in [first setup on the Mac](macos.md#first-setup-on-the-mac).

The bootstrap user environment installs the public GPG key, the card tools, and `install-user-age-identity`, and on Linux the bootstrap system layer runs pcscd. On macOS, GPG reaches the card through the system's own PC/SC framework, with no pcscd. With a YubiKey inserted, run the recovery helper from the clone in user mode. User mode needs `--host`, because the distribution owns the hostname:

```sh
./scripts/recover-age-identity --user --host <host>
```

GPG decrypts `secrets/bootstrap/<host>/age-key.asc` as the invoking user, and the helper pipes the result to `install-user-age-identity` instead of `sudo`. The installer checks that the identity derives the recipient in `secrets/bootstrap/<host>/recipient.txt`. Only then does it replace `~/.config/nix-config/age/key.txt` atomically, in a 0700 directory, with mode 0600 and owned by the user. An invalid identity leaves the existing file untouched. Nothing read from stdin is printed.

Then apply the production output:

```sh
nr switch
```

On a macOS host, `nr` refuses to move from a bootstrap generation to production unless you name the host, so the first production apply there is `nr switch --host <host>`.

Production activation checks the identity before it changes any link. When the identity is missing, has the wrong owner or mode, or cannot decrypt the secrets, the apply stops, names the file and the recovery command, and prints no secret. On success it publishes:

- the tokens in `~/.local/state/cli-auth/` (directory 0700, files 0400);
- the gh and glab configuration, through `publish-cli-auth`;
- the host's SSH key at `~/.ssh/id_ed25519_nix_config` (mode 0600).

Later applies need no card. The identity and the published files are plaintext on disk, so their protection rests on the distribution's disk encryption, or on FileVault on a Mac.

## Git signing and SSH

Signing commits and tags requires a YubiKey carrying the signing subkey. Three cards carry it, and each card has its own User PIN, so a PIN disclosed from one card does not unlock the others. Automatic PIN entry therefore uses one Secret Service entry per card, with `service=gnupg-card-pin` and `username=<normalized card serial>`: three cards mean three entries. If no entry exists for that serial or the keyring is locked, normal pinentry prompts for the PIN. Automatic submission never repeats after a PIN error or a retry-limit warning, and a prompt whose serial cannot be read unambiguously is never answered, because offering one card's PIN to another would burn that card's retry counter.

When a card rejects a PIN that was submitted automatically, the entry for that serial alone is discarded and the prompt falls back to ordinary pinentry. The other cards' entries are left in place. Re-registering the affected card is manual, with the same command below.

Register each card once in h82's desktop session, repeating the command with that card inserted. Enter the PIN at the command's prompt, not in its arguments or shell history.

```sh
nix develop
card_serial='<normalized serial from gpg --card-status>'
secret-tool store --label='OpenPGP card PIN' service gnupg-card-pin username "$card_serial"
unset card_serial
```

Each card serial must match the value that `gpg --card-status` reports with that card inserted. Routine rebuilds work without any of these registrations.

### YubiKey PIN on macOS

A macOS host has no Secret Service, so the PIN entries above do not exist there. gpg-agent's pinentry is `scripts/pinentry-card-darwin`, a filter in front of the same `pinentry-card` proxy, with `pinentry_mac` as the prompt. The filter gives `pinentry_mac` a key id derived from the card serial, `n/gnupg-card-pin-<serial>`, so the native PIN dialog offers a "Save in Keychain" checkbox. The checkbox starts unticked on every prompt, because the configuration sets `UseKeychain` to false in the `org.gpgtools.pinentry-mac` defaults.

When you tick it, `pinentry_mac` saves that card's PIN in the login Keychain, with service `GnuPG` and account `gnupg-card-pin-<serial>`, and answers later prompts for that card from the Keychain without a dialog. Each card has its own item, as each has its own Secret Service entry on NixOS. When the card rejects a PIN, the filter deletes that card's item and the next prompt shows the dialog; a saved PIN is never offered to the card a second time. After a nixpkgs update changes `pinentry_mac`'s store path, macOS may ask once whether the new `pinentry_mac` may read the saved item.

To remove a saved PIN by hand, for example before handing a card to someone else, delete its Keychain item:

```sh
security delete-generic-password -s GnuPG -a gnupg-card-pin-<serial>
```

Sign in to the 1Password app once and enable the SSH agent under Settings > Developer for fallback destinations. The repository preserves the key selection in `~/.config/1Password/ssh/agent.toml`. The user signs in, unlocks the app, and approves fallback SSH requests. Bootstrap configurations still use `IdentityAgent ~/.1password/agent.sock` directly; production desktops use the host-first path described below. In the same Settings > Developer pane, turn on "Integrate with 1Password CLI" once; that toggle is what lets `op` authorize through the desktop app instead of asking for a manual `op signin`, and no build-time check can reach it. `op` authorizes only inside a desktop session with a running PolKit agent, so it does not work over plain SSH, on a tty, or from a systemd unit.

1Password, Kleopatra, Discord, and Telegram now start at login from `home/h82/desktop/kde/autostart.nix`, so none needs a manual launch. Home Manager owns `~/.config/autostart/1password.desktop`, `~/.config/autostart/kleopatra.desktop`, `~/.config/autostart/discord.desktop`, and `~/.config/autostart/telegram.desktop` and overwrites them on activation, which makes the apps' own "start at login" toggles inert. Leave Telegram's own toggle off: it writes a differently named entry that Home Manager does not own, so Telegram would be launched twice at login. Discord and Telegram also restart 5 seconds after a crash, through `~/.config/systemd/user/app-discord@autostart.service.d/restart.conf` and its Telegram equivalent. Those are drop-ins on the units `systemd-xdg-autostart-generator` creates from the desktop entries, so quitting either app normally still leaves it stopped. Claude Desktop also starts at login, through `~/.config/autostart/claude-desktop.desktop`. It starts with `--startup`, so only its tray icon appears. The Tailscale tray, `tailscale systray`, starts from `~/.config/autostart/tailscale-systray.desktop` on every host that runs `tailscaled`. Change the module, not the desktop entries or drop-ins.

The user is the Tailscale operator (`--operator=h82` in both the `tailscale up` and `tailscale set` flags), so the tray and `tailscale` commands change settings without sudo. That right extends to every process running as the user: any of them can change preferences, the exit node, or `tailscale serve` without a password, and a serve configuration persists across restarts because `tailscaled-set` reasserts only the declared flags. Check `tailscale serve status` when auditing a host. A Disconnect from the tray lasts until the next boot, when `tailscaled-autoconnect` brings the node back up with `tailscale up --reset`, which also clears an exit node chosen from the tray.

## SSH key on a NixOS desktop

Each production NixOS desktop declares `secrets/hosts/<host>/ssh.yaml` and its matching public key, `secrets/hosts/<host>/ssh.pub`. [Adding a host](adding-a-host.md#create-the-desktop-ssh-key-source) describes source creation. Register the public `.pub` file as an authentication key on GitHub and every server the host must reach. Keep the existing 1Password keys registered until the host key has been tested on those destinations. Registration and later revocation are operator actions; applying this configuration changes no external account.

Log in through SDDM with the account password. In KWallet Manager, use a wallet named `kdewallet` whose password matches the login password for automatic login unlock. A wallet with another password or a failed PAM unlock must be unlocked manually. The repository does not set the wallet password. From the configured user's active local Plasma session, provision the working key:

```sh
systemctl --no-ask-password start desktop-ssh-provision.service
systemctl --user status desktop-ssh-agent.service
stat -c '%a %n' ~/.ssh ~/.ssh/id_ed25519_nix_config
```

Expect directory mode 0700 and key mode 0600. The fixed system service receives the root-only decrypted source through systemd credentials, generates a random passphrase, stores it in `kdewallet` under folder `nix-config SSH` and the public key's SHA256 fingerprint, and atomically publishes the encrypted working key. It reuses a valid key/wallet pair. Ordinary system applies do not require the wallet to be unlocked. SSH also requests provisioning automatically if the working key or wallet entry is missing.

The user profile installs `ssh`, `scp`, and `sftp` launchers; ordinary Git over SSH uses the same `ssh` from PATH. Each SSH invocation combines the graphical-session primary agent with the selected 1Password agent identities, offering the host key first. When the host key is accepted and usable, 1Password may remain locked or stopped. If the server rejects it or local signing fails, the same authentication exchange tries selected 1Password keys with its own unlock and approval requirements. Neither path retries an established session or reruns a remote command. A server's authentication-attempt limit must allow the primary key and the offered fallback set.

The primary agent socket is `/run/user/<uid>/desktop-ssh/agent.sock`; configuration is `~/.config/desktop-ssh/config.json`. Loaded primary keys are reused until graphical logout, including while the screen or wallet is locked. Logout stops the managed agent and clears its loaded key. Provisioning requires the configured account to have an active local graphical session; other accounts and requests made without that session are denied. While it exists, processes of that account can request provisioning from a tty, remote connection, or sessionless user service. The gate checks desktop presence for the account, rather than isolating callers by their own login session. This does not add key management for hosts without a graphical session. An explicit SSH `IdentityAgent` override or scp/sftp `-S` transport override selects the operator's own path. Tools that bypass the installed launchers do not receive automatic fallback.

If both authentication paths fail, unlock KWallet or 1Password as appropriate and inspect `journalctl --user -u desktop-ssh-agent.service` and `journalctl -u desktop-ssh-provision.service`. Do not print the decrypted source or wallet passphrase. See [desktop SSH recovery](recovery.md#restore-or-rotate-a-desktop-ssh-key) and the [manual desktop checks](verification.md#desktop-ssh-checks).

## SSH key on a non-NixOS host

A non-NixOS host has no desktop and so no 1Password agent. A macOS host is set up the same way. Each one has its own SSH key instead, stored encrypted in `secrets/hosts/<host>/ssh.yaml`. Production activation publishes it at `~/.ssh/id_ed25519_nix_config`, a name that never clobbers a key you made. `~/.ssh/config` names it with `IdentityFile ~/.ssh/id_ed25519_nix_config` and names no agent socket. [Adding a host](adding-a-host.md#create-the-host-ssh-key-file) creates the key.

Registering the public key stays manual. After the first production apply, print it:

```sh
ssh-keygen -y -f ~/.ssh/id_ed25519_nix_config
```

Add it to GitHub under Settings > SSH and GPG keys, and to `~/.ssh/authorized_keys` on every server the host must reach. Register it as an authentication key only. Git signing still uses the YubiKey.

## Compromise or decommission of a non-NixOS host

Follow these steps when a non-NixOS host, a macOS host, or a NixOS host is lost, compromised, or retired. A non-NixOS or macOS host keeps its identity and SSH key as plaintext on its disk. A NixOS host keeps its identity on its LUKS-protected disk, which a lost or sold machine puts out of your control. Either way, treat everything that host could decrypt as exposed.

1. Revoke its SSH public key on GitHub and remove it from every server's `authorized_keys`.
2. Remove the host's recipient from the rule of every shared file that lists it in `.sops.yaml`. Which files those are depends on the host kind. A non-NixOS or macOS host appears only in `secrets/tokens.yaml`, because `linux-host-secrets` keeps its recipient out of the other two. A NixOS host appears in `secrets/tokens.yaml`, `secrets/wifi.yaml`, `secrets/tailscale.yaml`, and `secrets/printers.yaml`. From the repository root, on any machine with the checkout and a YubiKey, re-encrypt each of those files to the remaining recipients, then replace its data key. The key command decrypts every host's bootstrap identity with GPG, and the card may prompt for its PIN:

   ```sh
   nix develop
   export SOPS_AGE_KEY_CMD="sh -c 'for f in secrets/bootstrap/*/age-key.asc; do gpg --batch --no-tty --decrypt -- \"\$f\"; done'"
   sops updatekeys -y secrets/tokens.yaml
   sops rotate -i secrets/tokens.yaml
   ```

   For a NixOS host, repeat the `sops updatekeys -y` and `sops rotate -i` pair for `secrets/wifi.yaml`, `secrets/tailscale.yaml`, and `secrets/printers.yaml` before you clear the key command. The `sops-recipients` check fails if any file's recipients still differ from its rule.

3. Rotate every token in `secrets/tokens.yaml` at its service. For a NixOS host, also rotate the Wi-Fi PSKs in `secrets/wifi.yaml` at their access points the key in `secrets/tailscale.yaml` at Tailscale, and any credential in `secrets/printers.yaml` at the printers. Write each new value into its file in the same shell without passing it as an argument: save it to a mode 0600 file outside the checkout, pipe it in as a JSON string, and delete the file. Then clear the key command:

   ```sh
   python3 -c 'import json, sys; sys.stdout.write(json.dumps(sys.stdin.read().strip()))' < <token-file> \
     | sops set --value-stdin secrets/tokens.yaml '["<key>"]'
   rm <token-file>
   unset SOPS_AGE_KEY_CMD
   ```

4. Delete `secrets/hosts/<host>/` and `secrets/bootstrap/<host>/`.

Removing a recipient without rotating the tokens revokes nothing. For a NixOS host, that includes the Wi-Fi PSKs and the Tailscale key. Git history keeps the old ciphertext, and the host's identity still decrypts it.

Keep steps 2 and 3 in this order. `sops set` encrypts to the recipients recorded in the file, not to `.sops.yaml`, so new values written first would still be encrypted to the removed host. `updatekeys` keeps the old data key, which the removed host can read from any earlier ciphertext in history; `sops rotate` replaces it.

Also delete `hosts/<host>/` and the `secrets/hosts/<host>/ssh.yaml` rule in `.sops.yaml`. Otherwise `bootstrap-recipients` fails on a host without bootstrap material, and `.sops.yaml` keeps a rule for a file that no longer exists.

## FIDO credentials on a card

`ykman` is installed system-wide, so listing a card's FIDO credentials needs no development shell. Yubico Authenticator is installed for h82 and shows the same list under its passkey view. Both are the upstream tools, unmodified.

```sh
ykman fido credentials list
```

**Only discoverable credentials can be listed.** A FIDO credential is either discoverable, in which case the card stores it along with the site it belongs to, or non-discoverable, in which case the card keeps no record of it at all and the site handed everything back at sign-in. Registrations made as a second factor are commonly the latter. A site missing from the list is therefore not evidence that the card has no credential for it, and no tool can close that gap.

Listing requires the card's FIDO2 PIN, which is a separate secret from the OpenPGP User PIN. The `gnupg-card-pin` entries described above hold the OpenPGP PIN only; nothing in this repository stores a FIDO2 PIN, and the tools prompt for it themselves.

Device access needs no setup. systemd tags any inserted security key and hands it to the logged-in user, independently of this repository's configuration.

## Verify after applying

Check each CLI's authentication status and test Git HTTPS access to the required hosts. Keep tokens out of status output and debug logs. Verify GPG signing in a temporary Git repository. On a NixOS desktop, verify both the host key with 1Password stopped and a fallback-only destination with 1Password approval; record the [desktop SSH checks](verification.md#desktop-ssh-checks) separately from repository tests.

## Coding agent harness configuration

Coding-agent harnesses (`claude-code`, `codex`, and `antigravity-cli`) are installed declaratively in `home/h82/default.nix`, and Pi is installed by `home/h82/agents/pi.nix` (see [Pi](#pi)). Pi is a manual path: it stays installed with its Synthetic provider, and you can start it by hand or name it for a task, but no rule in the shared instructions routes a worker, a scout, text generation, or a default peer to it. Grok is not installed on any host (see [Grok leftovers](#grok-leftovers)). Claude Code is configured in `home/h82/agents/claude.nix`, Codex in `home/h82/agents/codex.nix` (see [Codex](#codex)), and the Gemini and Antigravity CLIs in `home/h82/agents/gemini.nix`. The shared instructions come from `home/h82/agents/instructions/` (see [Shared agent instructions](#shared-agent-instructions)), and every Synthetic model that Pi names comes from `home/h82/agents/synthetic-models.nix` (see [Synthetic models](#synthetic-models)).

### Which tier owns which setting

Each Claude Code setting this repository declares is assigned to exactly one settings tier, and `home/h82/agents/claude.nix` holds all three lists.

- **Environment variables**, for settings whose persistent form is a variable: `DISABLE_AUTOUPDATER`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`. A variable that only overrides a single session, such as `ANTHROPIC_MODEL` or `CLAUDE_CODE_EFFORT_LEVEL`, does not move its setting into this tier. These are session variables, so they reach every program in the session, not only Claude Code — `DISABLE_AUTOUPDATER` in particular is read by other coding-agent CLIs as well; it lives in this module because the declared set belongs in one place.
- **The user settings file** `~/.claude/settings.json`, for everything else declared: `model`, `language`, `theme`, `preferredNotifChannel`, `agentPushNotifEnabled`, `inputNeededNotifEnabled`, `cleanupPeriodDays`, and `disableClaudeAiConnectors`, plus one leaf, `worktree.baseRef`, set to `head` so a native subagent worktree starts from the parent's current commit instead of the remote default branch.
- **The global config file** `~/.claude.json`, for keys Claude Code reads only from there and never from the settings file: `leftArrowOpensAgents`, set to `false` so the left arrow on an empty prompt no longer opens the agents view. A second activation entry runs the same merger against that file, so the merge, refusal, and compare-and-swap rules below apply to both files. Retiring works differently: `retiredKeys` feeds only the settings-file merge, so a retired `~/.claude.json` key goes in the `remove` list of the global-config declaration instead.

`advisorModel` is listed in `retiredKeys`, so each rebuild removes it from the settings file and the advisor stays off; an advisor chosen through `/advisor` lasts only until the next rebuild that produces a new generation.

`autoCompactWindow` is listed in `retiredKeys` too. It used to be declared as `400000`; each rebuild now removes the top-level key, so Claude Code compacts against the model's full context window. A window `/autocompact` saves for one model lives under `modelSettings`, where the merge assigns nothing, so that choice survives rebuilds.

`effortLevel` is listed in `retiredKeys` as well, and the Opus 5.5 leaf an earlier generation wrote is retired too. No settings tier declares a Claude effort any more, so every Claude model starts at the default Claude Code gives it, except where the shared instructions pass an effort for one `ce-work` launch (the `deep` worker, below). The top-level key went first, because Claude Code applies it only to models up to Opus 5. A later generation set `medium` for Opus 5.5 alone, under `modelSettings."claude-opus-5-5"`. The `removePaths` entry for `effortLevel` under that object carries `value` `medium`, the value this repository wrote, so the key goes only while it still holds that value and a level `/effort` saved for the model stays. It also carries `prune`, which removes each object on the path that the removals leave empty, after every removal has run so the result does not depend on declaration order: `modelSettings` goes when that leaf was its only key and a window `/autocompact` saved for a model stays. A level `/effort` saves for a model is the user's again. Both T3 Code `claudeAgent` model selections carry no Claude effort either. The shared instructions name exactly one Claude effort, `xhigh` for the `deep` worker's launch, and the `claude-effort-absent` check exempts only the `deep` sentence and the two launch sentences that pass its effort and fails when any other Claude effort returns.

Claude Code owns both files and rewrites them whenever a `/config` option changes, so Home Manager cannot place a read-only store symlink at either. Activation instead runs the packaged `agent-settings` merger, which assigns the declared keys and leaves every other key exactly as the agent wrote it. A key this repository neither declares nor lists in `retiredKeys` stays the user's permanently; a retired key becomes the user's once its `retiredKeys` entry is dropped. To hand a choice back to the user, retire it as described below and change `tests/claude.nix` in the same change; the `claude` check asserts the whole rendered set.

A declared key returns to its declared value on the next rebuild **that produces a new Home Manager generation**, not on every `nixos-rebuild switch`. `home-manager-h82.service` is a `RemainAfterExit` oneshot whose unit embeds the generation store path, so a rebuild that changes nothing in this repository leaves the unit untouched and activation does not re-run. Runtime drift in a declared key therefore persists until the next rebuild that actually changes something here.

Two consequences are worth knowing. A project-level `.claude/settings.json` outranks the user tier, so a repository you work in can still override a declared value for its own sessions. And the merger refuses to act when the settings path is a symlink or its contents are not valid JSON, which fails the rebuild rather than applying the declared values silently — remove the symlink or repair the file, then rebuild. A refusal leaves the file and its directory exactly as they were.

To stop declaring a key, move its name into `retiredKeys` in `home/h82/agents/claude.nix` rather than just deleting it from the declared set. The merge only ever assigns, so a deleted declaration would leave its last written value on every machine forever. Drop the `retiredKeys` entry once every host has rebuilt past it.

The merge is a compare-and-swap, not a plain read-modify-write: Claude Code may rewrite the file while activation is running, and a write that lands in that window is re-merged rather than discarded.

**Claude Code version bumps.** Claude Code is pinned in `packages/claude-code-manifest.json`, which `claude-code-release` rewrites and the dependency workflow commits as `chore(packages): bump claude-code to <version>`. Because no setting here declares an effort and only the `deep` worker's launch passes one, a release that changes a model's default effort changes every other session and worker on the next rebuild, with no diff in this repository to show it. Before a bump merges, check the release notes of the new version for a changed default effort of `opus`, `sonnet`, `haiku`, or `fable`. The workflow pushes a verified bump straight to main, so for that path read the notes on the bump commit before the next `nr switch` and tell the user what changed. Declaring an effort in settings again would reverse the retirement above, so it waits for the user; the `deep` worker's per-launch `xhigh` is the one effort the instructions already name.

**The managed settings tier is deliberately unused.** `/etc/claude-code/managed-settings.json` outranks every other tier and Claude Code only reads it, which is why this repository used it before. It blocks a change even inside a running session, so it does not scale to settings the user must still be able to adjust. Nothing declares it now, and NixOS removes obsolete `environment.etc` entries on switch, so an already-installed host loses the file on its next rebuild.

The `opus[1m]` value starts every session on the 1M-context variant of the `opus` alias, which follows the current Opus model. Drop the `[1m]` suffix to default to the standard context instead. The session runs at that model's own default effort.

### Surfaces that stay unmanaged

Only the scalar settings above are declared. Permission allowlists and hooks, MCP server definitions, plugins and marketplaces, other skills, and subagents are intentionally left as the user's mutable state; each needs its own mechanism and none is a key in the settings file. The three Korean writing skills are declared (see [Korean writing skills](#korean-writing-skills)), and `test-audit` is declared too (see [The test-audit skill](#the-test-audit-skill)); every other skill stays the user's. `~/.claude/CLAUDE.md` holds the shared instructions (see [Shared agent instructions](#shared-agent-instructions)).

### Codex

Codex is pinned to OpenAI's prebuilt releases for `x86_64-linux`, `aarch64-linux`, and `aarch64-darwin` (`packages/codex.nix`, `packages/codex-release.json`), so every host kind gets the same build. The pin carries two binaries for each system: `codex` and `codex-code-mode-host`. Activation runs the same `agent-settings` merger as Claude Code, in its `--format toml` mode, which keeps every comment and table it does not own. The declared set is `check_for_update_on_startup`, `features.in_app_updates`, `features.daemon_auto_start`, and `features.memories`, all `false`. Model, reasoning effort, sandbox and approval policy, trusted projects, and sign-in stay yours: run `codex login` once per host. A declared key returns to its declared value only on a rebuild that produces a new Home Manager generation, as for Claude Code. A malformed `config.toml` makes the merge refuse and fails the rebuild without touching the file. To stop declaring a key, move it to `retiredKeys` in `home/h82/agents/codex.nix`, which today lists `developer_instructions`, the key an earlier generation used to carry the system part of the instructions.

Codex reads the shared instructions from `~/.codex/AGENTS.md`, a Home Manager store link to the same rendering as Claude Code's (see [Shared agent instructions](#shared-agent-instructions)). `codex.nix` adds the `codex` token to `my.agents.crossModelPeers`, so `CROSS_MODEL_PEERS` allows Compound Engineering's `codex` route on every host that installs Codex. The compound-engineering plugin reaches Codex through `agent-plugin-sync --harness codex`, which registers the pinned source as a local marketplace and runs `codex plugin add`. Codex records the resolved store path, not the version-keyed link, so a version bump removes and re-adds both the marketplace and the plugin. Codex is the default cross-model review peer (`gpt-6.1-sol` at `reasoningEffort` `xhigh`, see [Shared agent instructions](#shared-agent-instructions)), so the account that `codex login` signs in must have `gpt-6.1-sol` open; that is a live check (see [Verification](verification.md)).

### Antigravity CLI

Antigravity is a manual backup. No rule picks it as a cross-model reviewer, a `ce-work` worker, a `ce-plan` scout, or T3 Code's text generator, and `CROSS_MODEL_PEERS` does not list `antigravity`. The CLI, its pinned settings, its copy of the shared instructions at `~/.gemini/config/AGENTS.md`, the ACP runtime wrapper, and T3 Code's `antigravity` instance with its runtime preinstall all stay, so you can start it by hand.

`agy` is pinned to Google's prebuilt releases for `x86_64-linux`, `aarch64-linux`, and `aarch64-darwin` (`packages/antigravity-cli.nix`, `packages/antigravity-cli-release.json`), so every host kind gets the same build, macOS included. The dependency workflow bumps the pin with `antigravity-cli-release`, which reads the feed at `https://storage.googleapis.com/antigravity-public/antigravity-cli/latest` and that version's `manifest.json`. When the feed fails, the workflow keeps the current pin and lets the other updates through. The wrapper sets `AGY_CLI_DISABLE_AUTO_UPDATE=true`, the only value `agy` honors, so `agy` never updates itself under any home, including T3 Code's per-instance homes.

The compound-engineering plugin reaches `agy` through `agent-plugin-sync --harness antigravity`. `agy` has no marketplace: it copies a plugin directory into `~/.gemini/config/plugins/<name>/` and records it in `~/.gemini/config/import_manifest.json`. The helper validates the pinned source's `.agy/` directory, installs it, and reads the installed `plugin.json` version back. When that version already matches, it installs nothing. On a version bump it installs over the old copy, which replaces the whole tree, and restores the old copy if the install fails. Retiring a plugin runs `agy plugin uninstall`. Whether a plugin is enabled lives in `~/.gemini/config/config.json`, which the helper never writes, so `agy plugin disable` survives later syncs.

Codex skills come from `~/.codex/skills`, the root `home/h82/agents/skills.nix` adds to the roots every other harness already has (see [Korean writing skills](#korean-writing-skills) and [The test-audit skill](#the-test-audit-skill)). No other harness reads that root, and dotagents' `~/.agents/skills` and its forbidden-root assertions stay as they are. Codex calls `~/.codex/skills` deprecated, but it still reads it, and the `codex-package` check (`tests/codex.nix`) fails when a pin bump stops doing so: it runs `codex debug prompt-input` offline against a skill linked into `$CODEX_HOME/skills`. The same check links the skill into `~/.agents/skills` as well and requires one listing, because Codex dedupes by canonical `SKILL.md` path and every root's link for a skill resolves to the same store directory. That is why a skill shows once on the MS-7D91 desktop, where `~/.claude/skills` also links into `~/.agents/skills` and Codex reaches the skill both ways. T3 Code's Codex sessions need no extra home: the generated `codex` instance declares `config.homePath = "~/.codex"` and `config.setupMode = "existing"`, so every apply overwrites a home set in the app, T3 Code sets `CODEX_HOME` to `~/.codex` over any `CODEX_HOME` in the instance's environment, and Codex runs with `~/.codex`, where the plugin sync and these skills already land. A `shadowHomePath` stays undeclared, because a shadow home shares `skills` and `plugins`. `~/.codex/skills/.system` stays Codex's own. The live check that Codex lists each skill once is in [Verification](verification.md).

Compound Engineering's Antigravity route, which only a pass you start by hand reaches, finds Google's Antigravity ACP runtime with `command -v agy_acp_server.par` and takes `localharness_external` from the same directory. `packages/antigravity-acp-path.nix`, installed on every host beside `agy`, puts both in the profile's `bin/`. Both point into the runtime `packages/antigravity-acp.nix` builds from `packages/antigravity-acp-release.json`, a pin of its own that follows Google's newest complete release (see [T3 Code](#t3-code)). T3 Code's managed layout links to the runtime T3 Code's own pin names, so the two are different store paths whenever Google publishes a release the pinned T3 Code does not yet require. T3 Code reads its `active.json` before it searches `PATH`, so the PATH copy changes nothing T3 Code shows or runs while the managed layout is in place. When that layout is gone, because the runtime was removed in T3 Code's settings or the installer failed, T3 Code falls back to the PATH copy, a newer runtime that the pinned T3 Code was not validated against, and reports its version as unknown until the next activation reinstalls the layout. `agy_acp_server.par` is a wrapper that execs the runtime by its store path, because the `.par` loads its embedded archive through argv[0] and acpx starts it by bare name. On Linux the wrapper also sets `SSL_CERT_FILE` when the caller left it unset or empty. It uses the first bundle that exists among `/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/cert.pem`, and `/etc/ssl/ca-bundle.pem`, then nixpkgs' `cacert`. The Linux runtime's own OpenSSL looks for a CA file that does not exist, and without one a session hangs after `session/prompt`. A runtime earlier on `PATH`, such as a manual download in `~/.local/bin`, shadows this one.

The route also needs Node 22.13 or newer and `npx`, which downloads `acpx@0.19.5` on first use. `nodejs` comes from nixpkgs, and mise's Node shadows it where mise is active. It also needs a Google sign-in. Compound Engineering starts the runtime with a fresh, private `GEMINI_HOME` on every run, and the runtime keeps its token in that home's `antigravity-acp/acp_token.json`. Sign in once per host so `~/.gemini/antigravity-acp/acp_token.json` exists: the `agy` CLI keeps its own login in the OS keyring or `~/.gemini/antigravity-cli/keyring-oauth-token`, while `agy_acp_server.par` writes `~/.gemini/antigravity-acp/acp_token.json` when started once with `GEMINI_HOME` unset. The `agy_acp_server.par` wrapper copies that file into each run's home before it starts the runtime, so no run asks for a sign-in again. It does this on every platform, only when `GEMINI_HOME` is named `gemini-home` and its parent directory is named after one of the scratch templates that Compound Engineering 3.31.0 passes to `mktemp -d`: `xmodel-cr-scratch-*` (`ce-code-review`), `xmodel-doc-scratch-*` (`ce-doc-review`), `xmodel-pov-peer-*` (`ce-pov`), and `ce-work-model-check-*` and `ce-work-adapter-*` (`ce-work`). It also requires that the parent, the home, and its `antigravity-acp` directory are real directories the user owns, that the parent has mode 0700, and that the home holds no `acp_token.json` yet. The copy has mode 0600 and is created exclusively, so the wrapper never overwrites a token. In the same recognized homes, whether or not a token was copied, it also links `humanizer`, `grammar-checker`, and `style-guide` from `~/.gemini/antigravity-cli/skills/<name>` into the home's `antigravity-cli/skills/` (created with mode 0700 when missing), skipping a missing source and never replacing an existing entry; that step is best-effort and never stops the runtime from starting. `config/skills` stays untouched. It never touches a T3 Code instance home or `~/.gemini` itself, and it is silent except for one line on stderr when a recognized home and a source token exist but the copy fails. A Compound Engineering release that renames those templates stops the seeding without any error, and the route then asks for a sign-in, as it does on a host that was never signed in. A host whose `~/.gemini` was never signed in pays Compound Engineering's 60-second wait (`CROSS_MODEL_SESSION_START_SECS`), the route is skipped as "waiting for a Google sign-in". Each run's copy goes away with Compound Engineering's scratch directory, and a token the runtime refreshes is not written back, so once the access token in `~/.gemini` has expired, each run refreshes it through Google. This assumes that Google does not rotate the refresh token when a copy refreshes, which only the hardware run can show (see [Verification](verification.md)). The macOS runtime may keep its token in the login keychain instead of that file, in which case the seeding does nothing there. A missing token and a missing CA bundle both look like a session that never answers. On the MS-7D91 desktop on 2026-10-19, with runtime 1.3.0 and Compound Engineering 3.31.0, a run that was signed in by hand, before the wrapper seeded each run's home, opened a session and then stopped before sending the prompt: Compound Engineering requested `gemini-4-argon` and `gemini-3.8-flash`, while runtime 1.3.0 advertised only tier-suffixed ids (`-low`, `-medium`, `-high`). Runtime 1.4 advertises the bare ids `gemini-4-argon` and `gemini-3.8-flash` that Compound Engineering requests and takes `thinking_level` (`low`, `medium`, `high`) as a separate session option, so the rule that told an agent to request a suffixed id is gone. The shared instructions (see [Shared agent instructions](#shared-agent-instructions)) carry no Antigravity rule, such as an effort override or a model pin, so a pass you start by hand runs at Compound Engineering's own defaults. The `antigravity-acp-path` check runs the wrapper against a stub runtime, including the seeding scenarios, and asserts that the pinned Compound Engineering plugin still creates its scratch homes under those five templates; `antigravity-acp-path-profiles` and `darwin-outputs` read every user's profile and assert that the wrapper defines and invokes `seed_acp_token`. A live run is a hardware check (see [Verification](verification.md)).

`home/h82/agents/cross-model-peers.nix` exports Compound Engineering's peer allowlist as `CROSS_MODEL_PEERS`, joined from the route token each agent module contributes, sorted, with bare commas: `claude,codex` on every host kind. `claude.nix` contributes `claude` and `codex.nix` contributes `codex`; `pi.nix` and `gemini.nix` contribute no token. Compound Engineering has no route for Pi, so a Pi peer the user names reaches Pi over ACP instead (see [Pi](#pi)), and a pass on the `antigravity` route needs that token added to the variable for that run. The `crossModelPeers` option's description names the two tokens. The module also exports `CROSS_MODEL_MAX_PEERS=2`, Compound Engineering's cap, which 3.31.0 reads only during discovery and dry runs. Compound Engineering 3.31.0 still picks one peer per pass, so outside T3 Code the shared instructions drive one pass per harness (see [Shared agent instructions](#shared-agent-instructions)). Both variables are set through `home.sessionVariables` and `systemd.user.sessionVariables`. On Linux, an app started from the desktop, such as T3 Code, sees a change only after the next login. On macOS a launchd login agent runs `launchctl setenv` for both, so apps started from Finder or the Dock after it runs get them too. A GUI app already running keeps the old value until it restarts, because `launchctl setenv` runs at login and reaches only apps started after it.

### Grok leftovers

Grok Build and Grok Bot are not installed on any host, and the flake holds no package, wrapper, instructions rendering, or cask mapping for either. T3 Code's `grok` instance is declared with `enabled = false`, so the app does not turn its built-in Grok instance back on. The `grok-absent` check fails when a name containing `grok`, matched without regard to case, reappears in any of these: a user package (by `pname` or `name`) of any NixOS host, non-NixOS host or fixture, or macOS host or fixture; a NixOS or macOS `environment.systemPackages` entry; a NixOS system or user unit; a cask or Mac App Store app in a macOS host's or fixture's evaluated `homebrew.casks` or `homebrew.masApps`; an app in `modules/shared/darwin-apps.nix`; or an `/etc` file or unit in a non-NixOS fixture's system-manager configuration. It also fails on a home file under `~/.grok` on any host. No legitimate name matches today, so its allowlist is empty.

On macOS the apply uninstalls the `grok-bot` cask when it is installed: `modules/darwin/retired-casks.nix` runs `brew uninstall --cask --force grok-bot` as the primary user after Homebrew's own step, never with `--zap`, and prints one line instead of failing the apply when brew fails (see [macOS hosts](macos.md)). The cask declares only its `Grok Bot.app` and a `zap` list of `~/Library` paths, with no `uninstall` stanza (homebrew-cask `Casks/g/grok-bot.rb` at `37b48ceb2d85`), so the uninstall removes the app bundle and Homebrew's records and leaves `~/Library` alone; `--force` adds only unpinning a pinned cask and purging its Caskroom directory. When `brew list --cask grok-bot` fails for any reason other than the cask being absent, the step prints brew's error and the command to run instead of treating the cask as gone. No apply deletes user data, so these stay until you remove them by hand:

- `~/.grok`, Grok Build's state directory on every host kind. It holds the sign-in token in `~/.grok/auth.json` at mode 0600, plus Grok's logs and config. The `grok` CLI is gone, so `grok logout` is no longer available: delete the directory with the token in it, and revoke the sign-in on xAI's side if you want the grant gone as well.
- Grok Bot's app data, which is not in the repository. Grok Bot is an Electron app, so its data sits in a directory named after the app, `~/.config/` on Linux and `~/Library/Application Support/` on macOS, with caches and preferences beside it. No repository check recorded the exact names, so list candidates before you delete one: `find ~/.config ~/.cache ~/.local/share -maxdepth 1 -iname '*grok*'` on Linux and `find ~/Library -maxdepth 2 -iname '*grok*'` on macOS.
- On a non-NixOS Linux host, the Grok Bot AppArmor profile the retired system-manager module loaded. The next system-manager apply removes `/etc/apparmor.d/nix-grok-bot` and the unit file and stops `nix-grok-bot-apparmor.service`: the pinned system-manager (`c397860e5113`) stops every service of the previous generation that the new one lacks, unless the unit sets `X-StopOnRemoval=false`, which this one did not (`crates/system-manager-engine/src/activate/services.rs`), and deletes every `/etc` file of the previous generation that the new one lacks (`activate/etc_files.rs`). Stopping the unit does not unload the profile, because the unit had no `ExecStop`, so the kernel keeps it until the next boot, and the parser's cache entry stays. The profile is `unconfined` and matches only a store path that no longer exists, so it changes nothing. A partial activation can still exit 0 (see the [system-manager learning](../.compound-engineering/artifacts/solutions/best-practices/system-manager-activate-exits-zero-on-partial-failure.md)), so after the apply check that `systemctl status nix-grok-bot-apparmor.service` reports no such unit and that `/etc/apparmor.d/nix-grok-bot` is gone. To unload the profile before a reboot, run `echo -n nix-grok-bot | sudo tee /sys/kernel/security/apparmor/.remove`.

### T3 Code

T3 Code tracks the upstream nightly channel. `packages/t3code-release.json` pins one nightly release for both artifacts, and the dependency workflow bumps it with `t3code-release`, which takes the newest GitHub prerelease tagged `v<semver>-nightly.<date>.<build>` and skips stable and preview builds. A host opts in with two traits (see [Adding a host](adding-a-host.md)):

- `my.t3.desktop.enable` installs the desktop app (`packages/t3code.nix`), on NixOS and macOS hosts only. On NixOS it is an `appimageTools` wrapper. The wrapper sets `T3CODE_DISABLE_AUTO_UPDATE=1`, so the app never updates itself, and points `CONTAINER_HOST` at the session Podman socket, so a container started by an agent inside its sandbox cannot disturb the host Podman service. On macOS it is the nightly release's app bundle, `T3 Code (Nightly).app`, which Home Manager copies into `~/Applications/Home Manager Apps`. That copy is writable, so a launchd agent runs `launchctl setenv T3CODE_DISABLE_AUTO_UPDATE 1` at login to keep the app from updating itself off the pin.
- `my.t3.cli.enable` installs the headless `t3` server (`packages/t3code-cli.nix`), patched to run without nix-ld so it also works on non-NixOS hosts. It updates only when you run `t3 update`, which installs an unmanaged runtime under `~/.t3`; let the flake pin move it instead.

T3 Code rewrites its settings files under `~/.t3/userdata/` at runtime, so `home/h82/t3code.nix` merges the settings that differ from the pinned nightly's schema defaults into `settings.json` and `client-settings.json` on activation and leaves every other key as the app wrote it. A value left at its default follows T3 Code when that default changes. Each declared provider instance states its `enabled` leaf even where it equals T3 Code's default, so a cleanup of default-valued settings keeps it. `claudeAgent.enabled` and `codex.enabled` are such leaves, because T3 Code turns those instances on by default. Declaring them means the instances no longer follow a change to that default, and a Claude or Codex instance turned off in the app is turned back on at the next activation that produces a new generation. The model selections (`defaultModelSelection`, `textGenerationModelSelection`) are owned whole, because T3 Code writes a selection with options that belong to its model. Neither `claudeAgent` selection carries an `effort` option, so both run at their model's own default, and the owned write drops an `effort` an earlier generation left in either. The default selection is `claude-opus-5-5` on `claudeAgent`. Text generation, which writes commit messages and titles, is `claude-haiku-5-5` on `claudeAgent`, so it costs Claude subscription usage at the smallest tier instead of a Synthetic request. It now runs at Haiku 5.5's default, `medium`, where an earlier generation pinned `low`, so titles and commit messages are slightly slower and costlier; the live check in [Verification](verification.md) shows that Haiku serves it. An earlier generation ran text generation on the `pi` instance with the model source's DeepSeek entry, and the Antigravity text-generation selection is gone before that. The `antigravity` instance keeps only its runtime preinstall and its home links. The `storageCleanup` block declares `worktreeOnMerge`, `worktreeOnDelete`, `worktreeUnchanged`, `worktreeAfterDays` of 8, and `worktreeSettledAfterDays` of 1. T3 Code removes the worktree of a thread that was settled a day ago, so an agent that settles each `delegate_task` child once it has read the child's result (see [Shared agent instructions](#shared-agent-instructions)) leaves no worktree behind for a person to clean up. A day gives the user time to reopen a settled thread before its checkout goes. T3 Code keeps a worktree with uncommitted changes, and it keeps every branch. It also keeps a worktree whose checked-out branch differs from the one it recorded, which is why the instructions tell an agent to keep the branch name T3 Code generated. A declared key changed in the app returns to the declared value on the next activation, and only a rebuild that produces a new generation runs activation. Of `providerInstances`, the merge declares only the leaves the shared instructions need (see [Shared agent instructions](#shared-agent-instructions)), `antigravity.{driver,enabled}`, which turns on the built-in Antigravity instance, `claudeAgent.{driver,enabled}`, which turns on the Claude instance explicitly, `codex.{driver,enabled}`, which turns on the Codex instance, `pi.{driver,enabled}`, which turns on the Pi instance, and `grok.{driver,enabled}` and `opencode.{driver,enabled}`, each with `enabled` false: T3 Code enables an unconfigured Grok instance by default and Grok is not installed, and OpenCode is no longer installed, so the disabled declaration turns off the instance an earlier generation enabled. The merge also retires `providerModelPreferences.opencode`, where an earlier generation hid OpenCode's text-generation alias, and drops `providerModelPreferences` when that leaves it empty; another provider's preference stays. `codex.config.launchArgs` is declared empty, which overwrites the `developer_instructions` launch override an earlier generation wrote with the old instructions; Codex reads `~/.codex/AGENTS.md` instead. Every other instance field stays as T3 Code wrote it. The instance `environment` list is upserted by name, so an entry the user added in the app stays, and a later entry with the declared name is dropped, because T3 Code applies the list in order and the last entry wins. The Claude instance's `launchArgs` leaf is owned whole: a launch argument added to it in the app is replaced on the next activation, so add one in `t3code.nix` instead. `providers` is the retired per-kind block that T3 Code moves into `providerInstances` on load, but only into an instance that does not exist yet. The merge creates the `antigravity`, `claudeAgent`, `codex`, `grok`, `opencode`, and `pi` instances, so it first moves those six kinds itself, the same way: `enabled` stays on the instance, every other field goes under `config`, and an existing instance wins. Other kinds stay in `providers` for T3 Code to move. App state stays the app's: onboarding marks, `projectSettingsFolded`, `favorites`, window bounds in `desktop-settings.json`, and `keybindings.json`.

Activation also installs the Antigravity ACP runtime that T3 Code uses. `packages/t3code-release.json` pins it per system under `antigravity`, which moves with the PATH pin (`packages/antigravity-acp-release.json`); `scripts/t3code-release` copies the existing antigravity section forward when bumping T3 Code, and `packages/antigravity-acp.nix` fetches the same archive T3 Code verifies. `scripts/t3code-antigravity-install` writes T3 Code's managed layout, `~/.t3/tools/antigravity-acp/<platform>/active.json` and `versions/<sha256>/` with `.install-complete.json`, and links the two binaries into the store package instead of copying about 1 GB. It leaves a version directory that T3 Code installed itself alone, and relinks one that points at an older package. The provider then shows the runtime as installed and needs only a Google sign-in, which stays manual.

T3 Code declares an enabled `codex` instance, which starts the packaged `codex` wrapper it finds on `PATH`, so the instance carries no `binaryPath` (see [Codex](#codex)). It serves the default cross-model review peer and any session you start on Codex. The `pi` instance is the manual path to Synthetic models: no rule points a task at it, and a task runs there only when you name a Pi model. It starts the `pi` wrapper it finds on `PATH`, so it carries no `binaryPath` and no launch argument, and no key reaches `settings.json`, because the provider's `apiKey` runs a key helper (see [Pi](#pi)). A task you send there names its model, such as `synthetic/hf:zai-org/GLM-5.3`, and its effort as `thinking` in `target.options`. T3 Code's `pi` driver launches `pi --mode rpc`, needs Pi 0.80.5 or newer, and loads an extension of its own that imports `@earendil-works/pi-coding-agent` and `typebox`, which the upstream standalone binary provides as built-in modules, so the packaged Pi needs no `node_modules`. The `grok` instance is declared disabled, since Grok is no longer installed (see [Grok leftovers](#grok-leftovers)), and so is the `opencode` instance, since OpenCode is no longer installed (see [Pi](#pi)).

T3 Code starts the `codex` and `claude` it finds on `PATH` with the user's `~/.codex` and `~/.claude`, so its sessions get the shared agent instructions and plugins below without a separate copy, and it gives each session its orchestration tools through its own `t3-code` MCP server.

Antigravity is different: T3 Code runs each Antigravity instance with `GEMINI_HOME` set to its own directory, `~/.t3/userdata/providers/antigravity/<hex SHA-256 of the instance id>`, and the harness reads none of `~/.gemini` from there. T3 Code links only the skills directories into that home: `config/skills` to `~/.gemini/config/skills` and `antigravity-cli/skills` to `~/.gemini/antigravity-cli/skills`. The ACP runtime loads skills from both but loads no plugins, so a `config/plugins` link to the CLI's plugins gives a session none of their skills; this holds for runtime 1.3.0 and 1.4.0. Activation therefore runs `scripts/t3code-antigravity-link` after the plugin sync. It links every skill of every installed plugin by name into `~/.gemini/antigravity-cli/skills`, skipping a plugin `agy plugin disable` turned off in `~/.gemini/config/config.json`, which the CLI does not list a second time beside the plugin, unlike `~/.gemini/config/skills`. It removes a link there that points into the plugins directory but no longer names a plugin skill, and leaves a directory or a link elsewhere, which is the user's, reporting it when it holds a plugin skill's name. Four more rules next to it say how a subagent waits for a slow command. It tells each subagent to give a command that can take more than a minute, such as a test suite, a build, or a flake check, a timeout that covers its expected run before it starts the command, where its shell tool takes one and up to the tool's limit. When the harness moves a command the task waits on to the background, the task waits for it inside the turn with blocking foreground calls, each within the tool's limit, until the harness's record of that one command shows it finished, and then reads the command's output and exit status from that record. On Claude Code that wait is a Bash loop such as `until grep -q '^\[exited with code' <output-file>; do sleep 5; done` on the output file the Bash tool named, under a `timeout` below 600000 ms and repeated as needed. It never matches a process name, because `pgrep -f` on a command line also catches another task's run of the same command and misses the same suite started with other flags; `Monitor` and background notifications do not count either, because they hold nothing open when the turn ends. The task is told never to stop and rerun a background command it waits on, whether the harness moved it there or the task started it there on purpose, because a missing or short timeout does not make the command wrong. It stops one only when it was the wrong command, when it is still running at twice the expected time, or when a time limit its task prompt sets arrives, and then reports what it has, so no command is left running behind its final report. It reruns a command the harness killed at its timeout once, with a timeout that covers the run, with none where the tool allows that, or in the background on purpose when no timeout can cover it. A command the task expects to outlast the shell tool's foreground limit starts in the background on purpose instead of in the foreground, through the tool's own background option rather than a shell `&`, and the task waits for it the same way and never ends its turn while it runs. The rule does not apply to a server the task keeps running for its own work. The rules rest on what each harness does, read on 2026-10-22. Claude Code 2.1.308's Bash tool defaults to 120000 ms, runs a foreground command for at most 600000 ms, moves a longer command to the background, and ends a background command's output file with an `[exited with code N]` line. Its description says a foreground `sleep` is blocked and recommends `Monitor`, which streams notifications while the agent works and holds nothing open at a turn end. Antigravity CLI 1.4.5's `run_command` backgrounds a command after at most 10000 ms of `WaitMsBeforeAsync`, and `command_status` waits for it; a live run on 2026-10-22 saw a shell `&` child vanish when the call returned and a `pgrep -f` loop keep matching its own command line. The tool takes no timeout, so every Antigravity command longer than 10 seconds falls to the wait rule. The `agent-instructions` check runs the example loop against an output file with and without that exit line, and fails when a packaged Claude Code or Antigravity CLI binary no longer carries a string these facts rest on, so a harness update that changes them is reread before it ships. The fix lives in the instructions rather than in Claude Code's `BASH_DEFAULT_TIMEOUT_MS` or `BASH_MAX_TIMEOUT_MS`, because those cover Claude Code only, Antigravity keeps its own limits, and a larger default holds every hung command longer. The incident behind the rules: a Claude Code child ran a pytest suite with no `timeout`, the Bash tool moved it to the background at 120000 ms, and the child stopped it with `TaskStop` and ran it again, so the suite ran twice ([#303](https://github.com/hyperlapse122/nix-config/issues/303)). When `delegate_task` rejects that launch with an error about the requested runtime mode, such as one saying the target provider does not offer it or that it ranks above the parent thread's mode, the agent relaunches the task once without `runtimeMode`, so it inherits the parent thread's mode, under a new `clientRequestId`; that rejection is not a failed or unavailable launch under any rule in the instructions, including the launch-failure retry and a failed cross-model peer, though a failure of the relaunch is one, and the `clientRequestId` reuse rule names the relaunch as its exception (`orchestrator_capabilities` lists no `runtimeModes` for `claudeAgent` and `antigravity`, yet both accept `runtimeMode: "full-access"` from a Full Access thread and report it through `t3_thread_configuration`, while an unoffered mode or one ranked above the parent thread's is rejected rather than silently narrowed). Every delegated task other than a cross-model peer starts in the parent's checkout, with no `isolation` argument, so a read-only reviewer or scout waits for no worktree; a cross-model peer keeps its own worktree, because it runs `full-access` on another provider with an untrusted diff in its prompt, and a peer launch that fails is a failed peer, never a run in the shared checkout. These worktree and shared-checkout rules sit in the Subagents section and cover every subagent: a subagent gets its own worktree through the native tool's `isolation: "worktree"` when it offers one, and otherwise through `delegate_task`'s. A subagent gets its own worktree only in three cases: two running subagents edit the same files (each commits its edits and reports its branch, and the agent fast-forwards the branches in one at a time from a clean checkout, rebasing each onto the tip the previous one left, or runs the tasks one after another), a task runs a command that rewrites files beyond its own, such as a formatter, a code generator, a dependency update, a branch switch, or a mutation test run inside the checkout (it commits and reports its branch like the others, and the agent rebases and fast-forwards it in the same way), and a task needs the committed state while the parent holds uncommitted edits it must not see. Subagents that share the checkout leave committing, staging, and formatting files beyond their own to the agent, and, because a Nix build or check reads the whole working tree, leave formatting, builds, and checks to the agent while another task edits there. A worktree launch of a task other than a cross-model peer that still fails after the one relaunch is skipped and reported with the reason when the task needed the committed state or must rewrite files beyond its own, because running it in the shared checkout would break the sharing rule or hand it the uncommitted edits it must not see; only a task that got its worktree for parallel edits of one file runs in the parent's checkout once every other task there has finished. In a run with a person present, after launching, the agent does the work that needs no delegated result, then ends its turn so the user can talk to it while the tasks run, naming the tasks still running and, when one of them runs without `runtimeMode: "full-access"`, noting that such a task can pause on an approval, which shows "Subagent needs approval" in its thread and waits for the user, because T3 Code sends no notification for it. T3 Code's notification, whether it starts the next turn or arrives with a user message, names the tasks that finished or have a question; the agent reads each finished task once with `task_status`, ending the turn again while other tasks the waiting step needs are still running. A task can write its result and never reach a terminal state, as a cross-model peer sometimes does, and then no notification arrives, so on every turn the agent gets while a task the waiting step needs is not terminal and its result is not taken (a notification, a user message, or a `t3_thread_wait` timeout), it reads that task's `task_status` once and then its session. A terminal task that shows `hasPendingChildRuns` false is used as usual, read from `latestTerminalSummary` instead of `summary` when that field is not null, because T3 Code fills it only with a later turn's result that differs from the first. When that result only promises a later report, as when the later turn never came, the agent reads the session, uses a finished message there that holds the whole result, and otherwise counts the task failed and says it ended without its report. A task that shows a pending question or `hasPendingChildRuns` true keeps being waited for. T3 Code sends no notification when such a later turn ends (pingdotgg/t3code#21772), so with a person present the agent names that task when it ends its turn and tells the user that no notification will come for its later turn, so they write once that turn has finished, or stop the task when its thread shows no progress; it starts no timer instead, under the rule below. Otherwise the agent reads the session with `t3_thread_read` on the task's `childThreadId`, in the `activity` view, paging with `afterPosition` until no `nextPosition` remains, and reads the latest assistant message by `itemId`, repeating with `textOffset` set to `nextTextOffset` until it is null, so a result longer than one page is read to the end. The `messages` view is not enough, because it hides tool calls, so a task still running tools after an interim message would look stalled. The agent takes the message as the task's result only when it is finished, holds the whole result the task prompt asked for, and nothing in the session has changed since the previous check. An unchanged session, not an item's `status`, is the test for a stall: it covers a stuck item that still shows `running`, and it keeps the agent from taking a message just before the next tool call starts. A take therefore needs two checks, a sibling's notification or a user message and then the next turn. The agent then stops the task with `task_cancel` and says it took the result from the session; when `task_cancel` leaves the task running, it keeps the result, tells the user once that the task still runs, and counts the result as taken, so no second take and no new wait follow. The rule keys on "not terminal" rather than on a `workState` value, because no stall's `task_status` was captured. In a run with a person present, the agent ends its turn while a needed task still runs and learns that it finished from T3 Code's completion notification, naming the tasks still running. A child's question arrives as a notification, and the agent answers it with `t3_pending_request_read` and `t3_pending_request_respond` or passes it to the user, then forwards the user's answer with `t3_pending_request_respond`. The agent never uses `mode: "wait"`, never waits with `t3_thread_wait` while a person is present, never calls `task_status` in a loop, and never starts a sleep, timer, or background command whose only purpose is to wake itself later; a delay a test must reproduce, a retry interval, a wait the user asked for, a wait that blocks on the task's own run, and a foreground wait inside the turn on a command the agent runs stay allowed. Ending the turn this way is allowed even under a skill that forbids ending the turn or fails when no blocking wait exists, such as `lfg` before `<promise>DONE</promise>` or `ce-code-review`'s reviewer collection; for such a skill a notification plus one `task_status` read that shows `hasPendingChildRuns` false, or a result taken from the task's session, is the task's terminal outcome, a task past the skill's time bound on resume counts as failed unless its session holds a whole result, and the run continues from the step that waited. In a run with no person present, nobody needs the conversation, so the agent waits inside the turn instead: `t3_thread_wait` on each task's run with the smaller of 600000 and the time left before any bound as `timeoutMs` (no wait when no time is left, and no new wait once the bound has passed), a pending question answered from the task and its instructions, a task whose `task_status` shows `pendingApproval` cancelled with `task_cancel` and counted as failed, because nobody can approve it, a check after each timeout and again when a skill's bound passes, where a whole result is taken even if the session changed and otherwise the task is cancelled as failed, and a wait without `runId` while the task still has a newer run. When no run is left to block on (`childRunId` null, `waiting_for_children` with `hasPendingChildRuns` false, or a wait without `runId` that returns at once without `timedOut` while the task is still terminal with `hasPendingChildRuns` true, as when the child sits idle between turns while its background command runs), there is no run to block on, so the agent makes one check, takes a finished message that holds the whole result, counts the task failed only when the bound has already passed at that check and the session holds no whole result, and otherwise ends the turn with no timer and no further check, naming the tasks when a person is present. Once the agent has read a delegated task's result or counted the task failed, a cancelled one included, it settles the task's thread with `t3_thread_organize` and action `settle`, and never its own thread. Deleting a thread takes a person and has no API, and an archived thread still counts as live, so settling plus `storageCleanup.worktreeSettledAfterDays` (see [T3 Code](#t3-code)) is the route that lets T3 Code remove the child's worktree. ### Tokscale

`home/h82/agents/tokscale.nix` puts a `tokscale` wrapper on `PATH` (`scripts/tokscale`, packaged by `packages/tokscale.nix`). It runs `bun x tokscale@latest` with three additions:

- `TOKSCALE_DEVICE_NAME` is the host name baked in at build time: the configuration's `networking.hostName`, which is the host's directory name under `hosts/`.
- `TOKSCALE_EXTRA_DIRS` gains, after any value you already exported, an `antigravity-cli:<dir>` entry for each existing `~/.t3/userdata/providers/antigravity/*/antigravity-acp/conversations` and for `~/.gemini/antigravity-acp/conversations`. T3 Code runs Antigravity through its ACP server with a per-provider `GEMINI_HOME`, so those conversations land outside `~/.gemini/antigravity-cli/conversations`, the only Antigravity CLI directory Tokscale scans; they use the same database format, so Tokscale counts them as Antigravity CLI usage. A path containing a comma is skipped, because the variable is comma-separated.
- `TOKSCALE_API_TOKEN` is read from `/run/secrets/cli-auth/tokscale_token` on each run, unless you exported a non-empty value yourself. No `~/.config/tokscale/credentials.json` is written.

The shared profile, `modules/nixos/profile.nix`, sets `my.cliAuth.enableTokscaleToken` to `true` by default on every host, which on a production output decrypts `tokscale_token` from `secrets/tokens.yaml` to that path, owned by h82 with mode 0400. `publish-cli-auth` never reads it, so a Tokscale problem cannot block gh and glab. To add or rotate the token, save it to a mode 0600 file outside the checkout and write it into `secrets/tokens.yaml` from the repository root without passing it as an argument. The key command decrypts every host's bootstrap identity with GPG, and the card may prompt for its PIN:

```sh
nix develop
export SOPS_AGE_KEY_CMD="sh -c 'for f in secrets/bootstrap/*/age-key.asc; do gpg --batch --no-tty --decrypt -- \"\$f\"; done'"
python3 -c 'import json, sys; sys.stdout.write(json.dumps(sys.stdin.read().strip()))' < <token-file> \
  | sops set --value-stdin secrets/tokens.yaml '["tokscale_token"]'
rm <token-file>
unset SOPS_AGE_KEY_CMD
```

A rotated token takes effect on the next `tokscale` run after the rebuild that decrypts it. On a bootstrap host, or with the flag off, the file is absent and Tokscale runs unauthenticated: local reports work and commands that need an account report "Not logged in". Commands run through `bunx` directly, rather than through the wrapper, are unauthenticated too.

Tokscale owns `~/.config/tokscale/settings.json`, so activation runs the same `agent-settings` merger as Claude Code. It reasserts `colorPalette`, `autoRefreshEnabled`, `autoRefreshMs`, `scanner.bucketTimezone`, and `autosubmit.enabled`, and leaves every other key, runtime state included, as Tokscale wrote it. As with Claude Code, a declared key returns only on a rebuild that produces a new Home Manager generation. Do not change the declared `scanner.bucketTimezone` casually: Tokscale refuses to move it without a server resync, because submitted day rows are monotonic. `~/.config/tokscale/custom-pricing.json` is a read-only store link holding the declared model prices.

Autosubmit stays off. Its scheduler would run Tokscale outside the wrapper, without the token.

### Pi

Pi is a manual path to Synthetic models. It stays installed on every host kind (`home/h82/agents/pi.nix`), but no rule in the shared instructions routes a cross-model peer, a `ce-work` worker, a `ce-plan` scout, or text generation to it; it runs when you start it, or when you name a Pi model for a peer or worker in the conversation. Inside T3 Code it runs on the `pi` instance; outside it, a Claude Code, Codex, or Antigravity session starts it as an ACP agent through the recipe in the shared instructions' `# Pi over ACP` section.

**Package and pin.** Pi comes from upstream's release tarballs, not nixpkgs. `packages/pi-release.json` pins version 1.4.0 and one tarball per system (`x86_64-linux`, `aarch64-linux`, and `aarch64-darwin`), each with the hash of the digest in the release's `SHA256SUMS`, and `packages/pi.nix` installs each tarball's `pi/` directory whole under `libexec/pi`. The binary is a Bun-compiled executable whose JavaScript payload rides at the end of the file, so the package never strips it. On Linux it and the X11 clipboard addon are patched to the store's loader; on macOS nothing is fixed up, so the code signature stays valid. The dependency workflow bumps the pin with `pi-release`, which reads GitHub's latest release and its `SHA256SUMS`; when that fails, the workflow keeps the pin and lets the other updates through. The `pi-release` check runs the helper's fixture tests.

**Wrapper and keys.** The `pi` wrapper (`scripts/pi`) exports only `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`, so Pi neither asks pi.dev for a newer version nor sends telemetry. It exports no key. The provider's `apiKey` is `!` plus the store path of the packaged key helper, `pi-synthetic-key`, which Pi runs for every request, so the key never sits in Pi's environment, where every command a tool runs would inherit it. The helper prints a non-empty `SYNTHETIC_API_KEY` the caller exported, and otherwise the key file: `/run/secrets/cli-auth/synthetic_api_key` on NixOS and `~/.local/state/cli-auth/synthetic_api_key` (`my.secrets.stateDir`) on non-NixOS and macOS hosts. A missing, unreadable, or malformed file means no key, and Synthetic then refuses the request: after trailing blanks are cut, a key must be 1 to 8,192 printable ASCII characters, the same rule the extension applies to the Exa key, whatever locale the caller set; a bootstrap generation holds no file, so Pi starts there and serves nothing. A key you export yourself does reach Pi's own environment and so the commands its tools run, which is why the ACP adapters unset theirs. The Exa key is not in the wrapper either: the extension reads `exa_api_key` from the same directory when a tool runs, and removes an exported `EXA_API_KEY` from its own environment when it loads. Neither key file is written. On NixOS, `my.cliAuth.enableSyntheticApiKey` and `my.cliAuth.enableExaApiKey` default to `true` in the shared profile, and a production output decrypts both from `secrets/tokens.yaml`. A non-NixOS or macOS production apply publishes both with `host-secrets`, which now requires six tokens and stops when any is missing (see [Adding a host](adding-a-host.md) and `secrets/README.md`). The `pi-wrapper` check drives the wrapper and the helper against a stub Pi and key files, both the sources and a copy of the packaged scripts with Pi and the key-file paths pointed into a scratch directory. With both key files present, Pi's environment must hold neither key nor a variable naming a key file; an exported `SYNTHETIC_API_KEY` must reach Pi unchanged and win in the helper. The `pi-extension` check runs one table of key files against both the helper and the extension, so the two copies of the rule cannot drift apart.

A non-NixOS or macOS production apply publishes each key at mode 0400, and `host-secrets` deletes the retired `opencode_api_key` file an earlier generation published. The key reaches neither the Nix store nor a command argument. To add or rotate the Synthetic key, save it to a mode 0600 file outside the checkout and write it into `secrets/tokens.yaml` from the repository root, as for the Tokscale token; the card may prompt for its PIN. The Exa key takes the same steps with `["exa_api_key"]`:

```sh
nix develop
export SOPS_AGE_KEY_CMD="sh -c 'for f in secrets/bootstrap/*/age-key.asc; do gpg --batch --no-tty --decrypt -- \"\$f\"; done'"
python3 -c 'import json, sys; sys.stdout.write(json.dumps(sys.stdin.read().strip()))' < <key-file> \
  | sops set --value-stdin secrets/tokens.yaml '["synthetic_api_key"]'
rm <key-file>
unset SOPS_AGE_KEY_CMD
```

A rotated key takes effect on the next Pi request after the rebuild that decrypts it. Synthetic's plan has a weekly credit limit, and a request that hits it fails.

**Model config.** Pi rewrites `~/.pi/agent/models.json` and `~/.pi/agent/settings.json`, so Home Manager owns neither. Two activation entries, `piModels` and `piSettings`, run the `agent-settings` merger on them after `installPackages`, and the merger assigns only the declared leaves.

- `models.json` declares the `synthetic` provider: `name`, `baseUrl` `https://api.synthetic.new/openai/v1`, `api` `openai-completions`, and the helper as `apiKey`. It upserts one model per entry of the model source by `id`, from the committed snapshot `home/h82/agents/synthetic-catalog.json`: the catalog's display name, context window, output limit, input modalities (`text` and `image`), and prices converted to USD per million tokens. `thinkingLevelMap` offers exactly the efforts the catalog lists. A listed effort maps to the Pi level of the same name, `max` included, and `xhigh` when listed; `off` sends `none` when listed; `minimal` and every unlisted level are unsupported. That is why a model can run at `max`. A model, provider, or key you add by hand survives every apply.
- `settings.json` sets `defaultProvider` to `synthetic`, `defaultModel` to the model source's `defaultModel`, `defaultProjectTrust` to `never`, and `modelThinkingLevels."synthetic/<id>"` for each model to its `defaultEffort`, except the text-generation model, which starts at the `text-generation` role's effort. The role dates from when T3 Code's text generation ran on Pi; text generation now runs on Claude Haiku (see [T3 Code](#t3-code)), and the role stays because it sets that model's startup level. `defaultProjectTrust` `never` means Pi never runs extensions or packages that a checkout supplies under `.pi/`, so a Pi peer reading an untrusted diff cannot be made to run code through them.
- `retiredModels` in `home/h82/agents/pi.nix`, today only `hf:moonshotai/Kimi-K3`, lists model IDs an earlier generation declared and the source no longer names. The merger's `removeEntries` operation drops each one's entry from the `synthetic` provider's `models` list in `models.json`, and a `removePaths` entry drops its `modelThinkingLevels."synthetic/<id>"` key from `settings.json`. When a source `id` moves to a newer build, add the previous one there, or its entry and its thinking level stay behind.

`nix run .#synthetic-models-watch -- --snapshot home/h82/agents/synthetic-catalog.json` refreshes the snapshot, and the update workflow runs it (see [Synthetic models](#synthetic-models)). The `pi-settings` check reads what each generation materializes, runs the real merger over the declared documents, and asserts the thinking-level maps against the snapshot, the hand-added model that survives, idempotence, and, with a fixture ID added to a copy of each declaration, that a retired ID leaves both files. Whether Synthetic honours the `reasoning_effort` that Pi sends for each level is a live check (see [Pi live probes](verification.md#pi-live-probes)).

**Extension.** `packages/pi-extension/index.js` is linked as a directory to `~/.pi/agent/extensions/nix-config` (`packages/pi-extension.nix` puts the host's two key-file paths into it), and Pi loads every directory there that holds a root `index.js`. It imports only `node:fs/promises` and declares its tool parameters as plain JSON Schema, so it runs from the Nix store with no `node_modules`. It registers three tools:

- `session_info` reports the session's `provider`, `model` ID, and `thinkingLevel`, and a value it cannot read is `null` with `error` saying why. When it fails, the shared instructions fall back to `PI_PROVIDER`, `PI_MODEL`, and `PI_REASONING_LEVEL` printed through the bash tool: Pi 1.4.0 exports them to every command its bash tool runs, resolved when the command starts, as its bundled `docs/environment-variables.md` and the `CHANGELOG.md` entry that added them state. A `pi-readonly` peer has no bash tool, so it has only `session_info`.
- `web_search` searches through Exa's HTTP API and returns each result's URL, title, and highlighted passages: five results by default, at most ten.
- `web_fetch` fetches up to five pages through Exa and returns each page's URL, title, and text, cut to 20,000 characters.

Each Exa request times out after 30 seconds, reported apart from a caller's abort, so a stalled connection fails the tool call instead of hanging a headless session. Both web tools label their output as untrusted web content, and refuse, without sending anything, a request whose text carries the Exa or Synthetic key verbatim, so a steered model cannot send either key out through a query or a URL. They load in every Pi session, so a Pi worker or peer you name can reach the web too; a session reading an untrusted diff could be steered into sending its content out through a query or a fetch URL, which is accepted. An ACP review peer on `pi-readonly` keeps only `web_search`, so a steered query is its one way out. The `pi-extension` check runs the extension's fixture tests under `node --test` and reads each user's materialized home. Whether Pi loads the directory and the tools reach the model is a live check.

**Skills and instructions.** The Compound Engineering plugin reaches Pi through `agent-plugin-sync --harness pi`. Pi has no plugin, subagent, or command format, so the helper links the same version-keyed path the other rows use and writes only its `skills` directory into the `skills` list of `~/.pi/agent/settings.json` through the merger. The three Korean writing skills and `test-audit` link into `~/.pi/agent/skills` (see [Korean writing skills](#korean-writing-skills)), and `~/.pi/agent/AGENTS.md` is a link to the shared body without the ACP section (see [Shared agent instructions](#shared-agent-instructions)). Whether Pi accepts skill directories that are links into the Nix store is a live check.

**Over ACP.** `packages/pi-acp.nix` and `packages/acpx.nix` build the ACP adapter `pi-acp` and the headless ACP client `acpx` with `buildNpmPackage`, from the registry tarballs that `packages/pi-acp-release.json` and `packages/acpx-release.json` pin and the lock files `scripts/npm-release` writes under `packages/pi-acp/` and `packages/acpx/`; the update workflow bumps both with `npm-release`. This `acpx`, 0.20.0, is separate from the `acpx@0.19.5` that Compound Engineering's Antigravity route downloads with `npx`. Both programs are on `PATH` on every host kind, and the shared instructions' `# Pi over ACP` section tells an agent in a non-Pi harness how to run them (see [Shared agent instructions](#shared-agent-instructions)). `acpx` has two agents:

- `pi` runs `pi-acp` by store path, never through `npx`, over this host's `pi` wrapper. It keeps Pi's `bash`, `edit`, and `write` tools and serves a `ce-work` worker you name.
- `pi-readonly` runs `pi-acp-readonly`, which adds `--exclude-tools bash,edit,write,web_fetch --no-mcp`. Neither `pi-acp` nor `acpx` can enforce read-only access on Pi's own tools, so removing the three built-ins by name is what keeps a review peer from writing files or running commands. Removing `web_fetch` keeps a peer steered by the diff it reviews from having Exa crawl a URL that carries a credential it read, and `--no-mcp` keeps an MCP server you add to `~/.pi/agent/mcp.json` from handing the peer a write tool. `session_info` and `web_search` stay, so the peer can still search the web and report its model. A `--tools` allowlist would drop those too.

Each agent's definition is patched into `acpx` at build time, and every rewrite must match the shipped text exactly, so a release that moves them fails the build. The patch also stops `acpx` reading `.acpxrc.json` from the directory it runs in, because that file's `agents` entries outrank the built-in ones and a checkout under review could otherwise rebind `pi-readonly` to any command it ships; `~/.acpx/config.json`, your own file, still applies. Both adapters unset `SYNTHETIC_API_KEY` and `EXA_API_KEY`, so a key the calling session exported never reaches the commands Pi's tools run; Pi reads its keys from the key files. The `pi-acp` check runs `acpx` over a recording stub Pi and over the packaged one, and asserts that each agent opens a session through Pi in RPC mode, that `pi-readonly` passes the exclusion, and that a checkout's `.pi/extensions/` and `.acpxrc.json` run nothing. Whether the `thought_level` a session sets reaches Synthetic as `reasoning_effort` is a live check.

**What removing OpenCode leaves.** The repository no longer installs, configures, or updates OpenCode, and apart from T3 Code's settings, where it turns off the `opencode` instance and retires its hidden-model preference, it cleans up nothing on a machine that ran it. The merged settings files under `~/.config/opencode`, the session data under `~/.local/share/opencode`, and any running `opencode` server stay for you to delete or stop by hand. The `opencode` command is no longer on `PATH`, so stop the server by process, for example with `pkill opencode`.

### Synthetic model watch

`.github/workflows/synthetic-models.yml` compares the models in `home/h82/agents/synthetic-models.nix` with Synthetic's catalog once a day (cron `23 4 * * *`) and on `workflow_dispatch`, and keeps one issue open while they differ. It holds only `contents: read` and `issues: write`, and it never edits code, bumps an ID, or opens a pull request. The comparison lives in `scripts/synthetic-models-watch`, which a flake app runs locally: `nix run .#synthetic-models-watch -- --help` lists the flags, and `--catalog <file>` compares against a saved catalog instead of fetching one.

The script fetches `https://api.synthetic.new/openai/v1/models` and classifies each model in use:

- **removed**: its ID is missing from the catalog.
- **new version**: the catalog has a build in the same lineage that is newer. A higher captured version is newer whatever its `created`; an equal version is newer only when its `created` is later, so an equal or missing `created` is not newer. A suffixed product such as `-Air`, `-Code`, or `-Flash` never matches another entry's lineage. GLM-5.3-Flash has its own `glmFlash` entry, whose lineage matches lower Flash versions such as GLM-4.7-Flash, which the watch never reports as newer.
- **changed**: the model's reported `reasoning_parameters.efforts` no longer contains an effort the repository assigns it, so a lost `max` is a finding for the `max` roles only.

`syn:` IDs are ignored. A row that carries `alias_of` never keeps a model in use present, but an `hf:` alias row in a model's lineage counts as a newer build. A catalog ID that is not `hf:<org>/<name>` of letters, digits, `.`, `_`, and `-` is counted but never printed, so no third-party text reaches an issue except inside code spans. A fetch that fails or answers 429 is retried once after a wait; a second failure or an empty catalog fails the run and leaves the issue's body and title as they were. When a reconcile issue is open, the failed run comments once that the watch cannot reach the catalog, and no further failure comments until a run reaches it again and says so; with no issue open, the failed run is the only signal.

The workflow runs the script in a step that alone receives the optional Actions secret `SYNTHETIC_API_KEY`, which the script sends as a bearer header on the fetch command's stdin and never in an argument. Without the secret the fetch runs keyless, which Synthetic's listing allows. CI gets no SOPS recipient, because `secrets/tokens.yaml` also holds the GitHub, GitLab, JPI, and Tokscale tokens; add the secret in the repository's Actions settings, as its own value, and rotate it there. A later step manages the issue with `GITHUB_TOKEN`: it ensures the label `model-reconcile`, opens one issue when there is drift and none is open, edits the open one and comments when its findings fingerprint changed, edits it without a comment when only its details changed (such as the efforts Synthetic offers), and, when the drift is gone, comments the commit SHA and closes it. When more than one issue with the label is open, it keeps the oldest and closes each other one with a comment naming it. The step reads the fingerprint, the body digest, and the last catalog notice back from the issue only through the script's `--issue-state`, so the script owns every marker. The issue's title and first line state the whole request, so `/ce-sweep` can process it through the `gh-issues` source in `.compound-engineering/config.yaml`; to act on one, confirm on Synthetic that the candidate ID it names is the model you expect, because the catalog publishes it, then change the single `id` in `synthetic-models.nix`. The `synthetic-models-watch` check fails when `home/h82/agents/synthetic-models.nix` itself drifts from a catalog snapshot from 2026-10-21, and runs the script's fixture tests, which read that file rather than a copy, for removed, new-version, changed, and clean results, the 429 and empty-catalog failures, the key staying out of argv and output, and the default `curl` and `nix eval` command lines. The `synthetic-models-reconcile` check runs the workflow's issue step with a stub `gh` for each of those issue paths and asserts the workflow's permissions. A scheduled workflow in a public repository stops after 60 days without repository activity, and the dependency workflow, which runs every 30 minutes, keeps this one active. If GitHub disables it anyway, the Actions page shows it as disabled; turn it back on with `gh workflow enable synthetic-models.yml --repo hyperlapse122/nix-config`.

### Memory

Persistent memory features are explicitly disabled so mutable per-user history does not affect agent behavior. Claude Code uses the `CLAUDE_CODE_DISABLE_AUTO_MEMORY` variable above; the Antigravity CLI sets `"disableAutoGenerateMemories": true` in `~/.gemini/antigravity-cli/settings.json`, and `~/.gemini/settings.json` sets `"experimental": { "autoMemory": false }`.

The two Gemini-side files reach the home directory differently, and `home/h82/agents/gemini.nix` holds both. The Gemini CLI only reads `~/.gemini/settings.json`, so a Home Manager store symlink holds it. The Antigravity CLI rewrites `~/.gemini/antigravity-cli/settings.json` itself — trusting a workspace replaces the whole file — so a symlink there is replaced by a regular file, and the next activation refuses to clobber it and fails the rebuild. That file therefore goes through the same `agent-settings` merger as `~/.claude/settings.json`, with the same consequences: the declared key returns to its declared value only on a rebuild that produces a new Home Manager generation, everything the agent wrote (trusted workspaces included) is preserved, and a retired key belongs in `retiredKeys` rather than simply deleted.

Existing memory stores on disk are intentionally left untouched. Disabling the features prevents the harnesses from interacting with or reading from those paths, avoiding destructive and non-idempotent removal logic during activation.

## Container runtime and registry authentication

Rootless Podman is configured declaratively in `modules/nixos/services/podman.nix` with Docker CLI compatibility enabled and the rootful systemd daemon socket disabled. Registry authentication is served through `docker-credential-sops` (`packages/docker-credential-sops.nix`), which answers Podman's credential queries by reading decrypted SOPS secrets at `/run/secrets/cli-auth/` without writing tokens into `~/.config/containers/auth.json`. A non-NixOS host gets no Podman from the flake, only the registry search, `auth.json`, and the credential helper. There the helper reads `~/.local/state/cli-auth/` instead, and `docker.io` pulls stay anonymous, because that host never publishes `docker_token`. A Podman you install there may also need the Ubuntu 24.04 AppArmor user-namespace setting in [adding a host](adding-a-host.md#first-setup-on-the-machine).

A macOS host runs containers in one rootful Podman machine on the libkrun provider, which Home Manager's `services.podman` creates and a launch agent starts at login; `home/h82/dev/containers.nix` configures it, and [macOS hosts](macos.md#containers) describes it. `docker` is a link to `podman`, so both read the same `auth.json` and ask the same credential helper, which reads `~/.local/state/cli-auth/`. Pulls run from the Mac send those credentials into the VM; the VM itself has no helper. As on a non-NixOS Linux host, `docker_token` is never published, so `docker.io` pulls stay anonymous.

Supported registries:

- `ghcr.io` (authenticated via `github_token`)
- `registry.gitlab.com` (authenticated via `gitlab_token`)
- `registry.jpi.app` (authenticated via `jpi_token`)
- `docker.io` (authenticated via `docker_token`)

### Developer prerequisites

1. **Docker Hub token**: To enable authenticated pulls from `docker.io`, generate an access token on Docker Hub and save it to a mode 0600 file outside the checkout. From the repository root, write it into `secrets/tokens.yaml` as `docker_token` without passing it as an argument. The key command decrypts every host's bootstrap identity with GPG, and the card may prompt for its PIN:

   ```sh
   nix develop
   export SOPS_AGE_KEY_CMD="sh -c 'for f in secrets/bootstrap/*/age-key.asc; do gpg --batch --no-tty --decrypt -- \"\$f\"; done'"
   python3 -c 'import json, sys; sys.stdout.write(json.dumps(sys.stdin.read().strip()))' < <token-file> \
     | sops set --value-stdin secrets/tokens.yaml '["docker_token"]'
   rm <token-file>
   unset SOPS_AGE_KEY_CMD
   ```

   Then enable Docker Hub token decryption in `hosts/<host>/default.nix`:

   ```nix
   my.cliAuth.enableDockerToken = true;
   ```

   Before that token is added and enabled, lookups for `docker.io` report a clean credential miss and fall back to anonymous pulls.
2. **Token scopes**: Ensure the existing GitHub token carries `read:packages` (or `write:packages` for pushes) and the GitLab tokens carry `read_registry` (or `write_registry`). Tokens issued solely for CLI or Git HTTPS access will return 401 Unauthorized upon pulling container images even when credentials are provided correctly.

## VSCodium

`home/h82/dev/vscodium.nix` installs VSCodium through Home Manager's `programs.vscodium`, with `codium` and a `code` wrapper on `PATH`, `nixd`, and the Nix IDE and Biome extensions. Other extensions, including GitHub Copilot and GitLens, stay user-installed from Open VSX; their settings are declared anyway and apply once they are installed. The extensions directory stays writable for them.

VSCodium owns `~/.config/VSCodium/User/settings.json`, so activation runs the same `agent-settings` merger as Claude Code. It reasserts the settings ported from the legacy dotfiles, and leaves every other key as VSCodium wrote it, including keys VSCodium or an extension adds inside a declared object such as `[nix]` or `json.schemaDownload.trustedDomains`. Array settings, such as `todo-tree.general.tags`, are reasserted whole. As with Claude Code, a declared value returns only on a rebuild that produces a new Home Manager generation. The merger reads plain JSON only: a comment or trailing comma in `settings.json` makes it refuse the file and fail the rebuild, naming the file, until the comment is removed.

On macOS, VSCodium's user directory is `~/Library/Application Support/VSCodium/User` instead of `~/.config/VSCodium/User`, for both files.

`~/.config/VSCodium/User/keybindings.json` is a read-only store link, forced over the regular file the legacy dotfiles left there. A keybinding added through VSCodium's keyboard shortcuts editor cannot be saved; add it to `home/h82/dev/vscodium.nix` instead.
