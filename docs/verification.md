`nix flake check` builds no NixOS VM test. The VM tests live in `tests/vm-checks.nix` and are exposed as `vmChecks`: build one with `nix build --no-link .#vmChecks.<name>`, or every one with `.#vmChecks.all`. They need Linux with `/dev/kvm` and the `nixos-test` and `kvm` system features. CI builds each in its own `vm-checks` job, derived from the same attribute names, and the update-dependencies workflow builds `.#vmChecks.all` before it pushes. `vm-checks-guard` fails when a `checks` entry carries the `nixos-test` system feature, and also when it cannot recognize every `vmChecks` entry that way.

CI does not run plain `nix flake check`. Its `flake-check` job runs `nix flake check --no-build`, which evaluates every output once, and its `check-shards` jobs build the checks, one job per entry of `checkShards` (defined in `tests/check-shards.nix`). The `hosts` shard holds the checks whose closure carries a NixOS system path or a Home Manager or system-manager generation, so those closures are fetched once; the remaining checks split by sorted name across the `light-<n>` shards. Build one shard locally with `nix build --no-link .#checkShards.<name>`. A new check joins a shard and CI without a workflow edit; list it in `hostClosureChecks` in `flake.nix` when it reads a host generation, or it lands in a light shard and makes that shard fetch the host closures. `check-shards-guard` fails when a check is in no shard or in two, or when a shard is empty or names something that is not a check.

Build every output under `nixosConfigurations`, `homeConfigurations`, `systemConfigs`, and `darwinConfigurations`, production and bootstrap; the loops build whatever the flake lists, so they need no edit when a host is added. `homeConfigurations` and `systemConfigs` hold the non-NixOS hosts and stay empty until `hosts/` has one; `darwinConfigurations` holds the macOS hosts in the same way. CI's build matrix is derived from the same attribute names. It builds each non-NixOS output on a runner of that output's architecture, aarch64 on `ubuntu-24.04-arm`. A macOS output builds only on a macOS builder. CI's `build-darwin` job builds every `darwinConfigurations.<host>.system` and every `checks.aarch64-darwin` entry on a `macos-15` runner, one job per target.

The checks iterate every configuration and decide what to expect from each configuration's traits (`my.*.enable`), `my.kind`, and `my.bootstrap`, never from its host name. A check that covers a trait fails when no production configuration enables that trait. `bootstrap-recipients` also fails when a directory under `hosts/` has no matching `secrets/bootstrap/` directory or the reverse, and `host-name-guard` fails when a host directory name or a fixture host name under `tests/fixtures/hosts/` appears in `flake.nix`, `lib/`, `modules/`, `home/`, `tests/`, `scripts/`, `packages/`, or `.github/workflows/`.

### Desktop SSH repository checks

`desktop-ssh-sources` validates every NixOS host's encrypted SSH source, exact host-only recipient rule, and distinct valid public metadata without decrypting real credentials. `desktop-ssh` reads materialized Home Manager files, user profile launchers, and systemd units for production, bootstrap, and non-NixOS fixtures. It also runs the packaged lifecycle/protocol tests with fake keys and wallets: atomic publication, recovery, cache invalidation, bounded agent handling, primary-first routing, and safe fallback. Mutation checks must fail in the builder with the intended diagnostic, rather than only fail Nix evaluation.

`desktop-ssh-integration` is a NixOS VM check using a real OpenSSH server and fake agents. It exercises primary authentication with fallback stopped or stalled, rejection and signing-failure fallback, SSH/Git/scp/sftp, bounded authentication attempts, separate invocation-agent process ancestry and cleanup, and a failed remote command whose side effect occurs once. `desktop-ssh-session` uses fake SOPS credentials and a fake KWallet D-Bus service with the declared modules. It checks root-only source access, real systemd credential delivery, graphical-session authorization, protected working-key publication, primary signatures, cached use with a locked wallet, local-state recovery, and logout cleanup despite a lingering user manager.

These checks do not establish that the physical SDDM session unlocks the real wallet or that 1Password attributes consent correctly to the original application or terminal tab. Those remain unchecked [desktop SSH checks](#desktop-ssh-checks). Neither VM uses real private credentials, registers a key externally, or activates the developer's host.

### Non-NixOS host checks

The non-NixOS checks run against two fixture hosts under `tests/fixtures/hosts/`, one per architecture, with fake age identities, tokens, and SSH keys. The fixtures are reachable only through `checks`, never through `homeConfigurations` or `systemConfigs`.

- `non-nixos-home-<fixture>` and `non-nixos-system-<fixture>` build each fixture's Home Manager activation package and system-manager toplevel. `checks.x86_64-linux` carries the x86_64 fixture. `checks.aarch64-linux` carries only these two builds for the aarch64 fixture; every other check stays x86_64. Build them on an aarch64 machine with `nix build --no-link .#checks.aarch64-linux.<name>`, or let CI build them on its arm runner.
- `non-nixos-outputs` asserts that every fixture yields a production and a bootstrap output for its own architecture, and that the account follows `my.user`. It asserts that no desktop configuration reaches the user environment, even with the laptop trait. It asserts that only production runs the secret activation steps, that `~/.ssh/config` names the host key rather than the 1Password agent, and that the system layer manages no file the distribution owns. On the builder's architecture it also reads the materialized system layer: pcscd with the ccid drivers, a `nix.conf` that keeps builds on the `nixbld` users, and `/etc/nix-config-host`.
- `host-options` asserts that each NixOS configuration's Home Manager user sees the same host facts and traits as the system, and that nothing under `home/` reads `osConfig`.
- `host-secrets` drives `scripts/host-secrets` in activation order against a scratch home. It covers a missing identity, an identity that is not a recipient, a wrong mode, and a symlinked identity, each failing without staging or printing a token. It then covers a successful stage and publish with the required modes, a repeat run, and a refusal to write the SSH key through a symlink.
- `nr-linux` drives `scripts/nr-linux` against a fixture root with commands printed instead of run. It covers host resolution from `/etc/nix-config-host`, each preflight refusal, and the refused `boot` and `test` subcommands.
- `linux-host-secrets` runs `tests/linux-host-secrets.sh` over the repository and over fixture trees built with fake keys. A non-NixOS host must have `secrets/hosts/<host>/ssh.yaml` encrypted to its own recipient alone, and its recipient must be in the `tokens.yaml` rule and not in the `wifi.yaml` or `tailscale.yaml` rules. Each broken tree must fail.
- `install-user-age-identity` runs `tests/test_install_user_age_identity.py` against the user-mode installer with a fake `age-keygen`.
- `non-nixos-vm` boots an Ubuntu 24.04 cloud image through nix-vm-test on x86_64 with KVM and applies the x86_64 fixture with the non-NixOS `nr`. Bootstrap applies without an identity. Production without an identity, or with the wrong one, stops before anything is published. After the identity is installed, production publishes the gh and glab configuration and the SSH key with the required ownership and modes, and `ssh` uses that key. Repeated applies keep the published files, and no apply changes the user database, subordinate id ranges, or `/etc/shells`. An aarch64 VM check does not exist; aarch64 is covered by builds only.

It asserts host discovery and both outputs; that every NixOS-only package has a decision in `modules/shared/darwin-apps.nix`; that the Homebrew casks are exactly the mapping's, with cleanup `"none"`, upgrades on, and every third-party tap tapped and trusted; that the user environment takes the non-NixOS path, with `nr` as `nr-darwin`, and the darwin pinentry with the Keychain checkbox unticked by default; that both outputs init one rootful libkrun Podman machine with 8192 MiB and 4 CPUs, reconcile an existing machine to them outside dry runs and with the user's temporary directory, keep the watchdog's VM alive across an agent reload at interactive priority, export the machine's socket to shells and GUI apps, and link `docker` to Podman, with the minikube login agent in production only and no OrbStack cask, credHelpers merge, or Docker Hub index alias; and that the system layer keeps store optimisation off, installs the shared fonts, and writes `/etc/nix-config-host`.
- `darwin-outputs`, the only check in `checks.aarch64-darwin`, builds both fixture systems and reads what they materialize: the activation order of the secret steps, the session's machine socket, the libkrun `containers.conf`, `docker` as `podman`, the Podman and minikube launch agents, the gpg-agent and pinentry configuration, Ghostty's font families, `nr` on `PATH`, the VSCodium settings path, the T3 Code bundle and its launch agent, `nix.conf`, `/etc/nix-config-host`, the Brewfile, and the fonts. It builds only on a macOS builder; CI builds it in `build-darwin`.
- `nr-darwin` drives `scripts/nr-darwin` against a fixture root, with commands printed or stubbed. It covers host resolution from `/etc/nix-config-host`, the age-identity preflight, the refusal to move a bootstrap generation to production without `--host` or `--bootstrap`, the register-then-activate order, and the refused `boot` and `test` subcommands.
- `pinentry-card-darwin` drives the darwin pinentry filter and its child proxy with a stand-in `pinentry_mac`, using fake PINs.
- `podman-machine-resources`, in `checks.x86_64-linux`, drives the helper that reconciles the Podman machine's memory and CPUs against a stub `podman`: matching values and an absent machine change nothing, a change stops and sets the machine without starting it, and a set that loses the race to the watchdog is retried up to three times.
- `minikube-darwin-start`, in `checks.x86_64-linux`, drives the minikube login helper against stub `podman` and `minikube`: it waits until `podman info` answers, bounding each call by the time left, starts the cluster once with the pinned profile, driver, runtime, and size, and fails without starting when Podman never answers or `minikube start` fails.

None of these activates a Mac. A nix-darwin activation that exits 0 is not proof that every step applied, so on real hardware confirm the state itself, as the list under [macOS hosts](#macos-hosts) does.
