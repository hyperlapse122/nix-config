# Concepts

Shared vocabulary for this repository. Each entry defines what a term means here, not what it means generally.

## Verification

**Repository check** — an automated assertion that runs from the flake and needs nothing but a checkout (and, for a VM check, hardware virtualization): it evaluates or builds configuration and fails the build when the result is wrong. Repository checks prove what the configuration *generates*; they can never prove how the installed machine behaves.

**VM check** — a repository check that boots one or more throwaway virtual machines to exercise behavior only a running system shows, such as a boot or a provisioning service. VM checks need hardware virtualization on the machine that builds them, so they are kept out of the everyday flake check and run on their own: each as a separate CI job, and before an automated dependency update may land. A VM check is still a repository check, so it still cannot stand in for a hardware check.

**Hardware check** — a manual confirmation performed on the physical machine after installation, recorded by the person who performed it. Hardware checks cover exactly what a repository check cannot reach: real devices, real firmware, real input. A passing build never substitutes for one, and results from the two are reported separately so neither is mistaken for the other.

**Mutation round** — one deliberate break of something a repository check claims to protect, run to confirm the check turns red, then restored. Rounds are counted per class of assertion rather than per assertion, and a check that has only ever been observed passing has not yet been shown to guard anything.

A round only counts when the check failed *for its own reason*. A break that stops the configuration from evaluating at all, or that trips a different assertion than the one under test, yields a failure that says nothing about the assertion being proven — so what a round establishes is read from where the failure came from, never from the fact that something failed.

A round that stays green is read the same way. The fixture a check runs against is part of what the round tests: when it seeds two sources the code chooses between with the same value, the broken and the correct version compute the same answer, and the round passes without the assertion ever having been able to tell them apart. So a green round is evidence only once the fixture is known to put those sources in states a wrong choice would distinguish.

The same holds when the operand, rather than the fixture, is fixed. An assertion that interpolates a value settled during evaluation — an option another module sets unconditionally — reaches the builder as a comparison of a constant against itself, so no round can turn it red. Whether an assertion is live is therefore a question about what the code under test can change, not about how many rounds have been run against it.

A round can also pass for a narrower reason: the observed value it checks is assembled from several parts, and the assertion is built only from some of them. A mutation to a part the assertion never included reaches the check and the check's shell can still fail — the assertion simply never depended on that part, so nothing about it could go red. Whether a round covers a claim is therefore also a question of which part of the observed value the assertion actually pins down, not only whether the mutation reached the check at all.

Turning a feature off and disabling one thing that feature produces are different breaks, because they leave different output behind: the first removes the artifact, while the second can leave a placeholder under the same name, such as a disabled service kept as an empty stand-in. An assertion that only asks whether something stands at that name passes the second while the feature is dead, so a round list that only toggles the feature has not tested it.

**Decorative assertion** — an assertion that is written as a check but cannot fail, so the check stays green whether or not the thing it names is correct. It is found only by a mutation round that breaks the guarded thing and watches the assertion stay green; a first green run cannot tell a decorative assertion from a live one. The causes vary (a negation the shell exempts from failing, a match that ignores the context that gives the matched text its meaning, a membership test that cannot see the order or repetition a passage's meaning depends on, a match that an identical line shipped by an upstream package also satisfies, an operand fixed during evaluation), but the remedy is the same: rewrite the assertion until a round turns it red for its own reason.

**Check evidence** — what a pull request's current head has actually been verified by, as opposed to what its check rollup appears to say. Evidence exists only when every workflow that runs on pull requests has a run registered against that head and every such run has finished; a rollup that is empty because the runs have not been created yet satisfies "all finished" without saying anything, so presence is a separate condition from completion.

Jobs that a finished run skips by design, such as the Nix jobs on a docs-only change, are part of that run's result rather than missing evidence. Readiness is judged on evidence in this sense rather than on a quiet period, because a quiet period measures that the pull request stopped moving, not that anything checked it.

## Signing key

**Card stub** — a keyring entry that records where a private key lives rather than holding it. The key material sits on a hardware token and cannot be read back out, so the entry names the token instead. Signing and decryption still work through it, and a listing distinguishes a stub from a real secret key, which matters because operations that move a key onto a token consume the local copy: once every entry is a stub, there is nothing left to move onto the next token.

**Offline backup** — the passphrase-protected export of the signing key, kept apart from the tokens that carry it. Because a token's private key cannot be extracted, there is no token-to-token path, and every replacement or additional token is provisioned from this backup. Losing it does not lose the key while a token still works, but it does mean the tokens in hand are the last ones that will ever exist.

## Desktop SSH

**Primary SSH key** — the host's own SSH identity on a NixOS desktop, offered ahead of every key the fallback agent holds and used only inside an active desktop session. Its public half is declared in the repository; its private half lives on disk encrypted with a random password that only the desktop wallet stores, and is re-derived from an encrypted recovery copy when that pair is missing or does not match. Signing with it therefore needs the wallet to be open and reachable, and when it is not, the agent refuses the primary key while keys from the fallback agent still work, so a signing failure that names the declared public key points at the wallet path rather than at the key itself.

## FIDO credentials

**Discoverable credential** — a FIDO credential the token stores itself, together with the site it belongs to, so the token can name that site without being told. Its counterpart, a non-discoverable credential, leaves nothing on the token: the site keeps the material and hands it back at sign-in. The distinction sets the ceiling on what any inventory tool here can report — a discoverable credential is listable, a non-discoverable one is unlistable by construction rather than by a gap in the tooling, so a site missing from a listing is not evidence that the credential is absent.

## Hosts

**Bootstrap host** — a second configuration built from the same module set as the production host, with private boot keys and user authentication secrets left out, used to install the machine before those secrets exist. It is not a separate machine or a reduced feature set: anything added to the shared modules reaches it too, so a change must be considered against an installer console as well as a logged-in desktop.

**Host trait** — a property a host declares about itself, such as having a NuPhy Gem80 keyboard attached or running the T3 Code desktop app, that modules and checks branch on in place of the host's name. Everything not covered by a trait comes from the shared host profile that every host imports, so two hosts differ only where a trait says they do; a difference with no trait behind it is drift, not configuration.

A trait need not be set by the host: the shared profile may default it from other traits or from whether the host is a bootstrap host, and a host may still override that default. A check guarding such a trait therefore confirms each input of the default separately, since sorting hosts by the trait's own value cannot reveal a default that turns it on too widely.

**Host facts** — the values of the shared host options (the host's kind, name, and bootstrap flag, its user account, its desktop SSH public key, and its traits) as one record the user environment reads on every host kind, and the base data the shared agent instructions are rendered from alongside the model source. Only an option every host kind declares is in it, so a fact that one host kind alone declares has to move into the shared options before the user layer or the instructions can read it. A template that reads a fact the record lacks fails the build, on any host where that read is evaluated, instead of rendering it as empty. A fact the record holds as null can still gate a section, because only printing a null fails.

**Non-NixOS host** — a host whose Linux distribution is not NixOS, found and declared like any other host but assembled as a standalone user environment plus a separately applied system layer instead of a NixOS system. It shares the user profile and traits with the NixOS hosts and never receives desktop configuration. The distribution keeps ownership of everything the system layer does not declare, including vendor stacks such as a JetPack NVIDIA driver.

## Generations

**Retention floor** — the number of most recent generations a cleanup policy keeps regardless of their age, as opposed to the age window it keeps alongside them. The two are a union, so the floor is what survives a long gap between rebuilds. It is not a free parameter: the boot menu's entries are rewritten only by a rebuild while collection runs on a timer, so a floor that does not cover the boot loader's own entry limit leaves the menu offering entries whose generations are gone — and those entries are the rollback path a system that will not boot has left. An unset limit is the unbounded case rather than a low one, and no finite floor covers it. The count floor applies to system and user profile generations; other garbage-collection roots, such as build results and development shells, ride on the age window alone, with the newest root of each development environment kept.

## Coding agent configuration

**Settings tier** — one of the layers a coding agent reads its configuration from, chosen per setting rather than per module. The tiers differ in who may write them and who wins, so the choice decides whether the user can still change a value at all: a tier the agent only reads outranks everything and locks the setting even inside a running session, while a tier the agent writes itself must be merged into rather than replaced. Which tiers a setting may go in is fixed by where the agent reads it, not where the agent lists or writes it: a key read only from the agent's own runtime-state file takes no effect when placed in its settings file. Some apps also read a per-repository file below their machine-wide settings file, so a value declared machine-wide silently overrides every repository's own choice; a setting a repository should decide stays out of the machine-wide tier. A setting is assigned to exactly one tier, and the assignment is recorded with its reason, because a tier chosen to dodge a write conflict silently also chooses how much control the user keeps.

**Activation reassertion** — the correction a Home Manager activation entry applies to user state that drifted since the last apply. How often it happens depends on the host kind. On a NixOS host it is conditional: the entry runs only when the rebuild produces a new Home Manager generation, because the service that carries it runs once, stays active, and has that generation's path in its definition. A rebuild that changes nothing in this repository leaves that service untouched and reasserts nothing, so a guarantee phrased as "on every rebuild" is false in exactly the case that motivates the entry — the user changed something at runtime and nothing else moved. A non-NixOS host and a macOS host run activation directly on every apply, so there the reassertion is unconditional, and a guarantee meant for every host kind has to be stated for the NixOS case.

**Cross-model delegation** — handing a piece of work to a coding agent served by a different provider or model than the one running the session, as distinct from delegated tasks that run on the session's own model or provider. When the session runs inside an orchestrating app that can launch other providers, the work goes through that app rather than through a skill's own way of finding and launching another tool. In a run with no person present, the peer tasks of that step share one deadline counted from the launch, and a peer still running when it passes is cancelled and counts as failed unless its conversation already holds a whole result, in which case that result counts even if the conversation changed shortly before; with a person present there is no deadline, and the user cancels a slow peer whose conversation holds no whole result. When the app's delegation tools are missing, the agent's native subagent tool does the work. The delegating agent stays responsible for the result and verifies it before relying on it.

**Delegated task** — a unit of work the session agent hands to a child agent through an orchestrating app, which runs it in its own child conversation and reports back to the parent. A task is finished only when its result is available, not when the child's current run ends: a run can end while the child's own nested work continues, a task can exist before its first run starts, and a run can stall on a question without ending. A task can also produce its result without ever finishing, so no completion notification comes. On every turn it gets while such a task is not finished, the parent reads the task's conversation, and takes its latest message as the result only when that message is finished and whole and the conversation has stayed unchanged between two checks, so a task that merely pauses between steps is not cut off, then stops the task, saying where the result came from. A deadline is the one exception: at a passed time bound the parent takes a whole result even from a conversation that just changed. Independent tasks are therefore launched together so they run at the same time. With a person present, the parent waits for them by ending its turn, which leaves the conversation open to the user, and resumes when the app's completion notification for each task arrives; no deadline cuts a task off, and the user cancels one that runs too long. Because a task that never finishes sends no notification, the parent also keeps a single timed wake pending while such a task runs, so it gets a turn to check the task's conversation even when nothing else arrives, and it stops that wake once no such task remains. With no person present, nobody needs the conversation, so the parent waits on each task's run inside its turn, in waits short enough that a task that never finishes is checked on a regular schedule, and a time bound counts the task failed only when its conversation holds no whole result. When the orchestrating app's delegation tools are available to a session that loads the shared instructions, every subagent the session agent starts is a delegated task, one level deep, and the agent's native subagent tool is used only when those tools are missing.

**Cross-model peer** — a reviewer a cross-model step sends one pass to, picked from a short candidate list: Claude Code on `claude-opus-5-5` at effort medium, OpenCode on GLM-5.3-Flash at high, and OpenCode on Kimi K3 at high by default, and OpenCode on GLM-5.3 at max only when the user names it. The step leaves out every candidate whose model family matches the session's, so the step gets readers that do not share the session model's blind spots. A model family comes from the model's maker, read from the model ID after one provider prefix such as `synthetic/` is removed (`claude-*`, `gemini-*`, or the org of an `hf:` ID: `zai-org` is `glm`, `moonshotai` is `kimi`, `deepseek-ai` is `deepseek`), and not from the harness that runs it, because one OpenCode instance serves models of several makers; an ID that maps to none is `unknown`. A session takes its family from the model it runs. Each family has its own defaults: a `claude` session runs GLM-5.3-Flash and Kimi K3, a `glm` session runs Claude Code alone, a `kimi` session runs Claude Code and GLM-5.3-Flash, and every other session, an `unknown` one included, runs Claude Code and Kimi K3. The step runs one pass for each peer inside an orchestrating app, and outside it one pass for each harness, with a single OpenCode pass pinned to the first picked OpenCode peer's model, whose report names each other picked OpenCode peer as not run. The user can name other peers for that run, which replace the defaults and number at most two; the report names a named peer that the family rule leaves out. Each peer runs on its pinned model ID only, and no other model takes a missing peer's place: when one is unavailable or fails, a pinned ID that returns 404 included, the step finishes with the peers that remain and the report names the missing one. A peer's findings join the review as evidence; they raise a finding's confidence only when the peer's family is known and differs from the session's, which inside an orchestrating app the peer's `task_status` receipt settles, and outside it OpenCode's route reports its family as `unknown`, so an OpenCode pass there raises none. They never authorize applying a fix unseen. Antigravity is never a peer; it stays installed for manual use.

**Review finding** — any item a review, verification, or check step of a Compound Engineering workflow reports about the work that workflow produces or changes, whatever its severity, its confidence, or the list the step files it in. A verdict that picks among options, such as whether to adopt a tool or which candidate wins, is not a finding. Review tools sort their output into a main list and side lists, such as testing gaps, residual risks, advisory notes, and observations shown for information, and the workflows that call them apply only part of the main list and park the rest for later. Here every one of those items is a finding and is applied in the same change. The only exceptions are an item verified to be wrong, one whose fix would weaken a safety check, one whose fix the user declined when asked, one whose fix would reverse a decision the user made in a run with no person present to ask, and one that no change in the repository can fix. A fix that would reverse a decision the user already made is asked about whenever a person is present, autonomous runs included, and is left unapplied as awaiting that decision only when nobody is there to ask; any other fix that needs a decision only the user can make is asked about in an interactive run, and an autonomous run applies the recommended fix and reports it. Each item left unapplied is reported under the tag of the exception it falls under: verified wrong, weakens a safety check, declined by you, awaits your decision, or no fix in this repository.

**Delivery path** — one way a coding agent session receives the shared instructions: a harness run from a terminal, or the same harness started by an orchestrating app. Every harness that gets instructions reads the same rendering of the shared template, while a rule that applies only inside an app is written as a condition on that app's tools rather than as a separate file for that path. A path whose runtime reads no instructions file, such as T3 Code's Antigravity instance, gets none.

**Provider instance home** — the private state directory an orchestrating app gives one provider instance in place of the agent's usual home, such as T3 Code's per-instance directory for Antigravity. The agent running there reads its configuration only from that directory, so anything this repository declares for the agent's usual home, such as global instructions or plugins, does not reach the instance unless it is carried there too. The app creates the directory when the instance first runs unless this repository has already prepared it, and it rewrites some of the files there every time it prepares the instance, so only configuration the app leaves alone lasts. A tool that shares the agent's name may still read only the usual home, so the instance's view can be checked only through the app or through the agent's runtime started directly against that directory. Carrying a file there does not prove the runtime reads it: T3 Code's Antigravity runtime has loaded the skills linked into its home but not the global instructions linked beside them.

**Declared set** — the settings this repository states a value for, as opposed to the ones it leaves alone. The distinction is what makes the boundary legible: a setting inside the set returns to its declared value on the next rebuild, and a setting outside it is the user's permanently. Growing the set therefore trades the user's freedom for reproducibility one key at a time, which is why membership is decided by stated categories rather than by whichever values happen to be convenient to declare.

**Model source** — the one pure data file, `home/h82/agents/synthetic-models.nix`, that names every Synthetic model the repository uses, each with its upstream ID, family, lineage pattern, the efforts its roles run at, and the effort OpenCode pins for it. OpenCode's settings, T3 Code's text-generation selection, the rendered shared instructions, the checks, and the model-watch workflow all read it, so moving to another build of a model is one changed value there, plus the previous ID in the retired-model list of `home/h82/agents/opencode.nix`, which removes the entry OpenCode's settings still hold for it. The DeepSeek entry pins one dated build and moves only when the user changes it after a reconcile issue reports a newer one; Claude model IDs are written inline and are not watched.

**Scout** — a subagent that only reads and summarizes for a skill's planning pass, here one of `ce-plan`'s repository, learnings, framework-docs, best-practices, and web researchers. Inside T3 Code it runs on the DeepSeek entry's `scout` role in the model source, with Claude Sonnet as its fallback: a scout that starts but returns no findings, or waits on an approval, is relaunched once there under a new request ID. No other subagent is a scout. The shared instructions pin the rule, and `docs/provisioning.md` has the routing.
