# Repository Guidelines

## Project structure

This flake configures personal machines, one per directory under `hosts/`. The NixOS host today is an MS-7D91 desktop workstation, and the daily driver is a MacBook Pro macOS host. Non-NixOS Linux hosts on x86_64-linux or aarch64-linux are also in scope: they get the same user environment without the desktop. macOS hosts on aarch64-darwin are in scope too: they get the same user environment through nix-darwin, plus the GUI apps through Homebrew. Preserve the default Plasma desktop on NixOS hosts. Desktop configuration on non-NixOS Linux hosts, desktop customization, and coding-agent settings are outside the migration.

- `flake.nix`: host discovery, checks, and development tools. Every directory under `hosts/` is a host named by the directory. A directory without `host.nix` is a NixOS host: `mkHost` builds a production `<host>` and a `<host>-bootstrap` output under `nixosConfigurations` and sets `networking.hostName` from the name. A directory with `host.nix` is the kind its `kind` field names, which `lib/hosts.nix` reads. `kind = "linux"` is a non-NixOS Linux host: `lib/linux-host.nix` builds `homeConfigurations.<host>` and `systemConfigs.<host>`, each with a `<host>-bootstrap` twin. `kind = "darwin"` is a macOS host: `lib/darwin-host.nix` builds `darwinConfigurations.<host>` and `<host>-bootstrap`, nix-darwin systems with Home Manager and nix-homebrew inside.
- `hosts/<host>/`: one machine. A NixOS host has its hardware (`hardware.nix`), disk layout (`disko.nix`), and traits (`default.nix`). A non-NixOS host has `host.nix` (`{ kind = "linux"; system = "x86_64-linux"; }` or `"aarch64-linux"`) and a `default.nix` that sets its account (`my.user.name`, `my.user.home`) and traits. A macOS host has `host.nix` (`{ kind = "darwin"; system = "aarch64-darwin"; }`; Intel Macs are not supported) and the same kind of `default.nix`, with `my.user.home` under `/Users`. [Adding a host](docs/adding-a-host.md) walks through all three.
- `lib/`: `hosts.nix` splits the host directories by kind. `linux-host.nix` assembles a non-NixOS host into its standalone Home Manager and system-manager outputs, and `darwin-host.nix` assembles a macOS host into its nix-darwin system. The flake and the checks' fixture hosts both use them.
- `modules/shared/`: `host.nix` declares the host options every assembly imports: `my.bootstrap`, `my.hostName`, `my.kind`, `my.user.name`, `my.user.home`, and every trait's `enable` option. `darwin-apps.nix` maps every NixOS-only package to a macOS cask, a Nix package, or a reason to leave it out, and the `darwin-config` check fails on a package without a decision.
- `modules/nixos/`: system modules by subsystem -- `hardware/` (udev, YubiKey, NuPhy Gem80, Sennheiser BTD, DualSense, Bluetooth audio, iPhone DFU restore), `system/` (base, boot, boot splash, sysctl/cleanup, nix-ld, agent-browser runtime deps, secrets), `desktop/` (Plasma/SDDM, fonts), `services/` (Podman, the rootless minikube cluster, printing, Tailscale, Proton VPN, systemd-resolved, the WiFiman Desktop daemon). Every NixOS host gets the one shared profile, `modules/nixos/profile.nix`, which `mkHost` imports: it imports every NixOS module and sets shared defaults with `lib.mkDefault`. There is no domain-level `default.nix` and no per-host import list. Hosts differ only through traits, the `my.*.enable` options that default to `false` (`my.nuphyGem80`, `my.t3.cli`, `my.t3.desktop`), and through per-host values the host file sets. Hardware-specific modules stay inert until a host enables their trait. Modules, Home Manager (through `config.my.*`, never `osConfig`), and checks branch on traits, `my.kind`, and `my.bootstrap`, never on a host name; the `host-name-guard` check fails when a host directory name or a fixture host name under `tests/fixtures/hosts/` appears in `flake.nix`, `lib/`, `modules/`, `home/`, `tests/`, `scripts/`, `packages/`, or `.github/workflows/`.
- `modules/darwin/`: the system layer of a macOS host. Every macOS host gets `modules/darwin/profile.nix`, which imports `nix.nix` (nix-darwin owns `nix.conf` with the shared settings and `auto-optimise-store` off), `host-marker.nix` (`/etc/nix-config-host`), `defaults.nix` (the place for macOS system defaults, none set yet), `homebrew.nix` (nix-homebrew installs Homebrew; the casks come from `modules/shared/darwin-apps.nix`, cleanup `"none"`), `xcode.nix` (a root step after Homebrew that installs or upgrades Xcode from the Mac App Store with `mas` and never fails the apply), `app-store.nix` (a root step after the Xcode step that installs or upgrades KakaoTalk from the Mac App Store the same way), and `fonts.nix` (the shared font list).
- `modules/system-manager/`: the system layer of a non-NixOS host, applied through system-manager. It runs pcscd with the ccid reader drivers, takes over `/etc/nix/nix.conf`, and writes `/etc/nix-config-host`. It never writes files the distribution owns, such as `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/subuid`, `/etc/subgid`, or `/etc/shells`.
- `home/h82/`: Home Manager modules by domain, each with its own `default.nix` that `home/h82/default.nix` imports -- `agents/` (Claude Code, OpenCode, Gemini and Antigravity CLIs, agent plugins for Claude Code and the Antigravity CLI, the shared agent instructions, one Go template over the host facts rendered into the one file every delivery path reads, as `docs/provisioning.md` describes), `desktop/` (Fcitx5, terminal, `kde/`), `dev/` (Git, containers, the Android SDK, which sits at `~/Library/Android/sdk` on macOS; `mobile-devices.nix` declares `my.mobileDevices`, the iOS Simulators and Android Virtual Devices a macOS host creates on apply), `security/` (GPG, SSH, non-NixOS secrets), `shell/` (Zsh/shell config). `desktop/` and the GUI packages apply to NixOS hosts only; a macOS host gets the terminal settings from `desktop/` and its GUI apps as casks. Import lists gate on the `hostKind` special argument (`nixos`, `linux`, or `darwin`), which each assembly sets to the same value as `my.kind`, because an import conditional on `config` recurses; everything else reads `config.my.kind`.
- `scripts/`: authentication and rebuild helpers, including `nr-linux` and `nr-darwin`, the apply helpers installed as `nr` on non-NixOS Linux hosts and macOS hosts; `packages/`: Nix packaging for those helpers and for `text-template`, the renderer of the shared agent instructions.
- `tests/`: Python, shell, NixOS VM, and non-NixOS VM checks. `tests/fixtures/hosts/` holds the non-NixOS fixture hosts, one per Linux architecture, and one macOS fixture host, which only the checks build.
- `docs/`: installation, provisioning, recovery, verification, and adding a host. `secrets/README.md` defines secret conventions.
- `.compound-engineering/artifacts/solutions/`: documented solutions to past problems (bugs, best practices, workflow patterns), organized by category (`best-practices/`, `boot-issues/`, `integration-issues/`, `logic-errors/`) with YAML frontmatter (`module`, `tags`, `problem_type`).
- `CONCEPTS.md`: shared domain vocabulary (verification, hosts, generations, coding-agent configuration); relevant when orienting to the repository or reading a learning that uses its terms.

The [implementation plan](.compound-engineering/artifacts/plans/2026-09-21-0149-feat-thinkpad-nixos-declarative-environment-plan.md) and [desktop plan](.compound-engineering/artifacts/plans/2026-09-22-1646-feat-ms-7d91-desktop-nixos-plan.md) record migration scope. The [host-generic composition plan](.compound-engineering/artifacts/plans/2026-09-28-0203-refactor-host-generic-composition-plan.md) records the shared profile, traits, and host discovery. The [non-NixOS Linux hosts plan](.compound-engineering/artifacts/plans/2026-09-30-2331-feat-non-nixos-linux-hosts-plan.md) records the second host kind, and the [macOS hosts plan](.compound-engineering/artifacts/plans/2026-10-07-1651-feat-macos-darwin-hosts-plan.md) the third. ## Build and development commands

- `nix develop`: enter the development shell.
- `nix fmt`: format Nix files with `nixfmt-tree`.
- `nix fmt -- --ci`: check formatting without edits.
- `nix flake check`: run declared checks. NixOS VM tests are not among them.
- `nix build --no-link .#vmChecks.all`: build every NixOS VM test; needs `/dev/kvm`. Build one with `.#vmChecks.<name>`.
- Pre-commit hook: `.githooks/pre-commit` runs `mise run lint-staged-markdown` to lint staged Markdown with `markdownlint-cli2`. The T3 Code `Setup` script enables it automatically; on other checkouts, run `mise trust && mise install`, then enable it with `git config core.hooksPath .githooks`. Skip it for a single commit with `git commit --no-verify`.

Before shipping, run `nix flake check`, build the VM tests, and build every output under `nixosConfigurations`, `homeConfigurations`, `systemConfigs`, and `darwinConfigurations`, production and bootstrap. List them, then build each:

```sh
nix build --no-link .#vmChecks.all
nix eval .#nixosConfigurations --apply builtins.attrNames
for host in $(nix eval --raw .#nixosConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#nixosConfigurations.$host.config.system.build.toplevel"
done
for host in $(nix eval --raw .#homeConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#homeConfigurations.$host.activationPackage"
done
for host in $(nix eval --raw .#systemConfigs --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#systemConfigs.$host"
done
for host in $(nix eval --raw .#darwinConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#darwinConfigurations.$host.system"
done
```

`homeConfigurations` and `systemConfigs` stay empty until `hosts/` holds a non-NixOS host, and `darwinConfigurations` until it holds a macOS host. `nix flake check` builds the x86_64 fixture hosts. An aarch64 output builds only on an aarch64 builder; CI builds those on its arm runners. A macOS output, and `checks.aarch64-darwin.darwin-outputs`, which builds the macOS fixture, build only on a macOS builder; off a Mac, leave them to CI's `build-darwin` job.

## Coding style and naming

Write all repository documentation in English, including READMEs, guides, plans, and captured learnings. Preserve exact commands, identifiers, and link targets.

Use two-space Nix indentation and let `nix fmt` control layout. Keep each module focused on one concern. Follow existing lowercase hyphenated module and helper names. Remove redundant comments, but keep comments that explain non-obvious constraints. Keep nixpkgs on unstable and change `flake.lock` intentionally.

## Testing guidelines

Add regression checks beside related tests and register new checks in `flake.nix`. Register a NixOS VM test in `tests/vm-checks.nix`, not under `checks`, so `nix flake check` stays fast; the `vm-checks-guard` check fails otherwise, and CI builds each VM test in its own `vm-checks` job. CI's `flake-check` job only evaluates (`nix flake check --no-build`); the `check-shards` jobs build the checks, one per entry of `checkShards` from `tests/check-shards.nix`, and `check-shards-guard` fails when a check is in no shard. Add a check that reads a host generation to `hostClosureChecks` in `flake.nix` so it builds in the `hosts` shard; reproduce a shard with `nix build --no-link .#checkShards.<name>`. The `build-darwin` job builds every `darwinConfigurations.<host>.system` and every `checks.aarch64-darwin` entry on a `macos-15` runner; `darwin-config` evaluates the macOS fixture on Linux under `checks.x86_64-linux`. Use fake tokens, PINs, and test keys. VM checks require Linux with `/dev/kvm` access and disposable disks. Report hardware verification separately from VM evidence; follow `docs/verification.md`.

## Commit and pull request guidelines

Use lowercase Conventional Commit subjects, matching the history's `feat(nixos):` and `chore:` prefixes. Write imperative, specific subjects, preferably under 50 characters and never over 72. PRs should describe behavior changes, link relevant issues, and report check and build results.

Always apply all review findings, in the same change, whatever a skill's own apply bar, confidence threshold, or list says, `lfg`'s included. This covers every finding from `ce-code-review`, `ce-simplify-code`, and `ce-doc-review`, residual risks and testing gaps too. When code review or adversarial analysis identifies failure modes, regressions, or architectural edge cases with concrete fixes, implement and verify them on the branch rather than deferring them as unapplied residuals. "By design", "no current instance", "low impact", and "the fix has a trade-off" are not reasons to leave a finding: when the first fix has a cost, look for one without it, and when none exists, apply the least costly fix and say what it costs. Leave a finding unapplied only when you verified it is wrong, quoting the evidence, or every fix for it would weaken a safety check, and report it with that reason in an `Unapplied review findings` section of the pull request body, which you omit when there are none.

When watching a pull request from a local session, judge readiness on check evidence rather than on a quiet period. No automated reviewer runs here; `check.yml` is the only workflow on pull requests and reports as checks, so the settle window here is zero. When `ce-babysit-pr`'s own watcher runs, arm it with `--settle-seconds 0`; this supersedes that skill's instruction not to pass `--settle-seconds` on the ordinary arm. When T3 Code's watch wakes you instead, start no settle-window wait beside it; the evidence rule below still decides readiness. Evidence counts only when every workflow that runs on pull requests has a run registered against the current head and every such run is terminal. Jobs a run skips by design, such as the Nix jobs on a docs-only change, are part of that run's result, not missing evidence. Nothing else relaxes: outstanding threads, comments, `needs-human`, and the base and branch-currency blockers keep their current force. While evidence is incomplete, do not declare readiness and do not re-arm at a shorter window.

## Security and lifecycle constraints

Never evaluate or build with real plaintext credentials. Ordinary rebuilds use the local LUKS-protected age identity. On a non-NixOS host, they use the user-owned identity at `~/.config/nix-config/age/key.txt`, which the distribution's disk encryption protects; a macOS host keeps it at the same path, protected by FileVault. YubiKey use is for initial recovery, Git signing, and decrypting the bootstrap identities for SOPS work; three cards carry the same key, each with its own PIN. Publish gh/glab files only after successful decryption and keep them writable by their user. Report failures without printing tokens.

Re-encrypt and edit SOPS files yourself, on any host, without sudo. From the repository root, set `SOPS_AGE_KEY_CMD` to decrypt every `secrets/bootstrap/*/age-key.asc` with `gpg --batch --no-tty --decrypt`; one card opens every host's identity, so together they reach every file in `.sops.yaml`. Then run `sops updatekeys -y <file>` to re-encrypt, or pipe a JSON-encoded value into `sops set --value-stdin <file> '["<key>"]'` to change one value. Do not use `sops edit`, which opens an interactive editor, or `sops decrypt` to the terminal. [Adding a host](docs/adding-a-host.md#add-the-recipient-to-sopsyaml-and-re-encrypt) has the exact key command.

Do not partition or format the developer's host, enroll firmware or TPM keys, or run `nixos-rebuild switch` or `nr switch` as validation. Hardware installation requires an explicit instruction.

Apply this counterfactual: if the learning document disappeared, would a future engineer reading the final implementation still be likely to repeat the mistake or redo substantial investigation? If not, do not invoke it. Completion, effort, and diff size alone are not enough. Capture at the checkpoint so a qualifying learning can ship in the PR that produced it, and only where the repository treats captured learnings as tracked, committed knowledge.

Write every report, summary, or handoff to the user through the `ce-noslop` skill. This applies when you are the top-level agent writing to the user, not when you are a subagent reporting to its caller. Do not apply it to code, config, verbatim quotes, or text the user asked to post as written.
