# Repository Guidelines

## Project structure

This flake configures personal machines, one per directory under `hosts/`. NixOS hosts today are a ThinkPad X1 Carbon Gen 11 laptop and an MS-7D91 desktop workstation. Non-NixOS Linux hosts on x86_64-linux or aarch64-linux are also in scope: they get the same user environment without the desktop. Preserve the default Plasma desktop on NixOS hosts. macOS, desktop configuration on non-NixOS hosts, desktop customization, and coding-agent settings are outside the migration.

- `flake.nix`: host discovery, checks, and development tools. Every directory under `hosts/` is a host named by the directory. A directory without `host.nix` is a NixOS host: `mkHost` builds a production `<host>` and a `<host>-bootstrap` output under `nixosConfigurations` and sets `networking.hostName` from the name. A directory with `host.nix` is a non-NixOS host: `lib/linux-host.nix` builds `homeConfigurations.<host>` and `systemConfigs.<host>`, each with a `<host>-bootstrap` twin.
- `hosts/<host>/`: one machine. A NixOS host has its hardware (`hardware.nix`), disk layout (`disko.nix`), and traits (`default.nix`). A non-NixOS host has `host.nix` (`{ kind = "linux"; system = "x86_64-linux"; }` or `"aarch64-linux"`) and a `default.nix` that sets its account (`my.user.name`, `my.user.home`) and traits. [Adding a host](docs/adding-a-host.md) walks through both.
- `lib/`: `linux-host.nix` assembles a non-NixOS host into its standalone Home Manager and system-manager outputs. The flake and the checks' fixture hosts both use it.
- `modules/shared/`: `host.nix` declares the host options every assembly imports: `my.bootstrap`, `my.hostName`, `my.kind`, `my.user.name`, `my.user.home`, and every trait's `enable` option.
- `modules/nixos/`: system modules by subsystem -- `hardware/` (udev, keyd, fingerprint, YubiKey, Thunderbolt, laptop lid policy), `system/` (base, boot, sysctl/cleanup, nix-ld, agent-browser runtime deps, secrets), `desktop/` (Plasma/SDDM, fonts), `services/` (Podman, Tailscale, Proton VPN, systemd-resolved). Every NixOS host gets the one shared profile, `modules/nixos/profile.nix`, which `mkHost` imports: it imports every NixOS module and sets shared defaults with `lib.mkDefault`. There is no domain-level `default.nix` and no per-host import list. Hosts differ only through traits, the `my.*.enable` options that default to `false` (`my.keyd`, `my.fingerprint`, `my.thunderbolt`, `my.nuphyGem80`, `my.laptop`), and through per-host values the host file sets. Hardware-specific modules stay inert until a host enables their trait. Modules, Home Manager (through `config.my.*`, never `osConfig`), and checks branch on traits, `my.kind`, and `my.bootstrap`, never on a host name; the `host-name-guard` check fails when a host directory name or a fixture host name under `tests/fixtures/hosts/` appears in `flake.nix`, `lib/`, `modules/`, `home/`, `tests/`, `scripts/`, `packages/`, or `.github/workflows/`.
- `modules/system-manager/`: the system layer of a non-NixOS host, applied through system-manager. It runs pcscd with the ccid reader drivers, takes over `/etc/nix/nix.conf`, and writes `/etc/nix-config-host`. It never writes files the distribution owns, such as `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/subuid`, `/etc/subgid`, or `/etc/shells`.
- `home/h82/`: Home Manager modules by domain, each with its own `default.nix` that `home/h82/default.nix` imports -- `agents/` (Claude Code, Gemini CLI, agent plugins, shared agent instructions), `desktop/` (Fcitx5, terminal, `kde/`), `dev/` (Git, containers, Android SDK), `security/` (GPG, SSH, non-NixOS secrets), `shell/` (Zsh/shell config). `desktop/` and the GUI packages apply to NixOS hosts only. Import lists gate on the `hostKind` special argument, which each assembly sets to the same value as `my.kind`, because an import conditional on `config` recurses; everything else reads `config.my.kind`.
- `scripts/`: authentication and rebuild helpers, including `nr-linux`, the apply helper installed as `nr` on non-NixOS hosts; `packages/`: Nix packaging for those helpers.
- `tests/`: Python, shell, NixOS VM, and non-NixOS VM checks. `tests/fixtures/hosts/` holds the non-NixOS fixture hosts, one per architecture, which only the checks build.
- `docs/`: installation, provisioning, recovery, verification, and adding a host. `secrets/README.md` defines secret conventions.

The [implementation plan](.compound-engineering/artifacts/plans/2026-09-21-0149-feat-thinkpad-nixos-declarative-environment-plan.md) and [desktop plan](.compound-engineering/artifacts/plans/2026-09-22-1646-feat-ms-7d91-desktop-nixos-plan.md) record migration scope. The [host-generic composition plan](.compound-engineering/artifacts/plans/2026-09-28-0203-refactor-host-generic-composition-plan.md) records the shared profile, traits, and host discovery. The [non-NixOS Linux hosts plan](.compound-engineering/artifacts/plans/2026-09-30-2331-feat-non-nixos-linux-hosts-plan.md) records the second host kind.

## Build and development commands

- `nix develop`: enter the development shell.
- `nix fmt`: format Nix files with `nixfmt-tree`.
- `nix fmt -- --ci`: check formatting without edits.
- `nix flake check`: run declared checks. NixOS VM tests are not among them.
- `nix build --no-link .#vmChecks.all`: build every NixOS VM test; needs `/dev/kvm`. Build one with `.#vmChecks.<name>`.

Before shipping, run `nix flake check`, build the VM tests, and build every output under `nixosConfigurations`, `homeConfigurations`, and `systemConfigs`, production and bootstrap. List them, then build each:

```sh
nix build --no-link .#vmChecks.all
nix eval .#nixosConfigurations --apply builtins.attrNames
for host in $(nix eval --raw .#nixosConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#nixosConfigurations.$host.config.system.build.toplevel"
done
for host in $(nix eval --raw .#homeConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#homeConfigurations.$host.activationPackage"
done
for host in $(nix eval --raw .#systemConfigs --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#systemConfigs.$host"
done
```

`homeConfigurations` and `systemConfigs` stay empty until `hosts/` holds a non-NixOS host. `nix flake check` builds the x86_64 fixture hosts. An aarch64 output builds only on an aarch64 builder; CI builds those on its arm runners.

## Coding style and naming

Write all repository documentation in English, including READMEs, guides, plans, and captured learnings. Preserve exact commands, identifiers, and link targets.

Use two-space Nix indentation and let `nix fmt` control layout. Keep each module focused on one concern. Follow existing lowercase hyphenated module and helper names. Remove redundant comments, but keep comments that explain non-obvious constraints. Keep nixpkgs on unstable and change `flake.lock` intentionally.

## Testing guidelines

Add regression checks beside related tests and register new checks in `flake.nix`. Register a NixOS VM test in `tests/vm-checks.nix`, not under `checks`, so `nix flake check` stays fast; the `vm-checks-guard` check fails otherwise, and CI builds each VM test in its own `vm-checks` job. Use fake tokens, PINs, and test keys. VM checks require Linux with `/dev/kvm` access and disposable disks. Report hardware verification separately from VM evidence; follow `docs/verification.md`.

## Commit and pull request guidelines

Use lowercase Conventional Commit subjects, matching the history's `feat(nixos):` and `chore:` prefixes. Write imperative, specific subjects, preferably under 50 characters and never over 72. PRs should describe behavior changes, link relevant issues, and report check and build results.

Always apply all review findings. When code review or adversarial analysis identifies failure modes, regressions, or architectural edge cases with concrete fixes, implement and verify them on the branch rather than deferring them as unapplied residuals.

When watching a pull request from a local session, judge readiness on check evidence rather than on a quiet period. Every reviewer here reports as a check, so arm the babysit watch with `--settle-seconds 0`; this supersedes that skill's instruction not to pass `--settle-seconds` on the ordinary arm. Evidence counts only when every workflow that runs on pull requests has a run registered against the current head, every such run is terminal, and no review check merely skipped; a skipped review is absent evidence, not a clean review. Nothing else relaxes: outstanding threads, comments, `needs-human`, and the base and branch-currency blockers keep their current force. While evidence is incomplete, do not declare readiness and do not re-arm at a shorter window. When a review check skipped, report the missing review evidence and hand back rather than withholding readiness with no report.

After an agent pushes to a pull request branch from CI, the push re-triggers the checks; wait for them and report what they said, never a result you did not see. Hand a failure you cannot reproduce with the fast Nix commands to `check.yml` rather than guessing at it. On reaching the wait ceiling, report the commit pushed, the runs still in flight, and where to watch them.

## Security and lifecycle constraints

Never evaluate or build with real plaintext credentials. Ordinary rebuilds use the local LUKS-protected age identity. On a non-NixOS host, they use the user-owned identity at `~/.config/nix-config/age/key.txt`, which the distribution's disk encryption protects. YubiKey use is for initial recovery and Git signing; three cards carry the same key, each with its own PIN. Publish gh/glab files only after successful decryption and keep them writable by their user. Report failures without printing tokens.

Do not partition or format the developer's host, enroll firmware or TPM keys, or run `nixos-rebuild switch` or `nr switch` as validation. Hardware installation requires an explicit instruction.
